# sync 配置与提取版本变化

配置失效描述的是**需要更新哪些索引内容**，不直接决定**必须新建数据库**。

- `CMakeLists.txt` 等仅纳入构建一致性检查、没有直接提取语义消费者的文本变化，不再强制重建，也不因此重新提取全部源文件。
- 忽略规则、语言范围变化会取消 scoped 限定，重新扫描完整文件集合，通过普通增量路径增删文件；不再调用隐藏的 `indexAll`。
- 实际影响解析/关系的配置（根目录 TS/JS 路径别名、包/工作区、Go/Rust 清单，以及实际支持位置的 C/C++ 编译数据库）变化，需要重新提取受影响的旧文件。当前保守地覆盖全部仍在范围内的已索引文件。
- 提取版本升级同样强制重新提取同内容文件，而不是仅靠内容 hash 跳过；此工作量计入规划，按项目配置的结构阈值选择增量或后台重建。
- 同步策略不读取历史耗时样本；运行环境变化本身不触发重建。

语义配置指纹、提取版本与已应用的语言范围都存储在 `codegraph.db` 的 `project_metadata`。只有本次完整成功后才更新；失败继续保留旧指纹/版本和重试标记。语义重提取在首次写入前持久化 pending 意图，即使中途改用另一配置、失败后又切回原配置，也会重做未完成的语义更新。配置在同步期间再次变化时，本次不能确认成功，下一次 sync 重新协调。

旧数据库没有语义配置快照时：若旧配置总指纹没有变化，可建立当前快照；若旧总指纹确实变化，不能证明变化仅是注释或范围规则，因此保守重新提取一次，但不会跳过结构策略直接要求 init。新快照建立后，CMake 注释等变化不再产生这种兼容性重提取。

后台构建仍保留源文件、配置与语义指纹一致性围栏。发布后的 catch-up 直接通过增量路径处理新增差异，避免“配置变化 → 再次重建”的循环。新库构建期间的旧库查询与最终短时切换机制不变。

新出现且带有实际语义清单的源目录，raw 增量路径可能在下一次 sync 保守重提取一次，以免提前确认未参与原始配置快照的新语义输入。

自动重建阈值由项目根目录的 `.codegraphrc.json` 单独配置，参见 [自动重建策略](adaptive-sync.md)。这个策略文件不属于上述解析语义或索引范围输入，改阈值只影响下一次同步的选路。
