# C/C++ 通用符号提取修复

2026-09-26 至 2026-09-27。实现基于干净的 `bfe0a38`，提取版本升级到 **24**。

## 修复范围与原因

之前的三方审计已在 OceanBase、MAME 和中性语法样例中复现以下问题。本次规则依赖声明结构、宏定义及源码作用域，没有项目路径、宏名或变量名黑名单。

| 问题 | 引入来源 | 修复 |
|---|---|---|
| 类内宏调用被当成方法，部分还被当成字段 | `97b8362` 扩大类内声明入口 | 统一检查宏调用证据；保留带返回类型的同名函数、构造函数、对象式字段宏和真实展开符号 |
| include 语句片段里的赋值被当成全局变量 | `ba38bde` 的赋值补救过宽 | 必须存在相邻的损坏类型声明和普通 `=`，才允许补救 |
| 宏在同一行生成类和函数头，后续函数体被截断 | `93d2913` 的稀疏重放 | 扫描整行的多段声明和完整闭合边界；隔离独立函数体语句干扰，保留空语句、展开行及类内声明证据 |
| 条件表达式、构造初始化列表中的限定调用变成方法 | `3b7b885` 的文本补救 | 要求返回类型前缀合法，且位于可执行体与预处理指令之外 |
| 损坏 AST 让局部变量逃逸 | `7e4aae1`、`18722eda` 等声明恢复路径，部分问题原版已有 | 独立扫描注释、字符串、指令、条件分支及平衡作用域；只用可确认的闭合区间排除局部变量 |
| 类外静态成员定义丢失类名 | `9715e685` 只保留声明符叶节点 | 保留完整限定名，正确合并当前命名空间；不删除真实静态成员 |

另处理两个关联问题：声明宏没有源代码分号时，不把宏名作为字段；语句宏替换产生的分号不能被借用为变量声明终止符。损坏声明中的直接类/结构体定义也会被保留。

全量差异复核进一步覆盖了超过 512 行的函数、多行原始字符串、被误吞入宏参数列表的后续类，以及被误吞入函数体的显式模板实例化。辅助解析只隔离可以确认的独立函数体语句，保留宏展开行和类内代码，避免连带删除宏生成的真实类型。

如果完整展开行明确包含命名类型定义，但辅助 AST 没有产出该类型，才触发一次更小的独立解析。该解析保留原始命名空间，只补回缺失类型及其包含的符号，并连接到原有命名空间节点；不导入其他函数或变量解释。宏自行提供起始括号的独立函数，在辅助声明输入中闭合，避免不确定的结束宏吞并后续类型。

完整的匿名命名空间展开则单独解析，同时保留其类外静态成员定义、显式实例化和注册对象；从原来的辅助输入中移走这些行，避免重复解析同一批展开。独立解析要求括号闭合且以声明终止符结束，仍以函数头结尾的展开继续保留后续源代码函数体。

兼容性复核还发现声明宏展开器的两个通用词法问题：定义中的 `//` 原先在整个外层展开结束后才清理，会吞掉外层声明的尾部；逐字符扫描也会把 `123suffix` 这样的预处理数字后缀误当成宏名。现在在代入定义前清理其行注释（保留字符串中的 URL），并把预处理数字作为完整 token 处理。宏扫描结果和原生扫描协议不变。

原先声明宏展开最多处理 4,096 次，达到上限后静默停止；前部识别结果变化会使原本能解析的尾部声明跌出额度。现将通用预算提高到 8,192 次，并在超限时产生 `declaration_macro_expansion_limit` 诊断。极大文件仍可能存在未展开的尾部声明，因此这次修复不保证全部宏生成符号都能提取。超过旧上限及达到新上限的中性用例均有覆盖。

宏展开节点的列号映射回原始调用行。同一宏调用行生成同名声明和定义时，按现有 ID 规则保留后面的定义。

## sync 与存量功能

同一个 MCP/watch 进程内，修改宏定义后原先会继续复用旧宏上下文。现在新增/修改宏定义文件、删除已有宏定义或删除 C 家族文件会使宏上下文失效。刷新在下一次有 C 家族文件需要解析时进行；普通消费者修改、无变化 sync、仅删除文件的 sync 保留原有扫描快路径。旧文件是否含宏使用索引查询判断，不加载其全部符号。

回归测试验证：宏签名和静态成员名变更，正反两个方向的 sync 与重新初始化得到相同节点、限定名、签名、位置和边；也覆盖删除最后一个宏、删除宏文件及无变化同步。编译后的 worker 路径另行验证通过。

该变更不引入宏依赖文件的自动全量重解析。仅修改宏头而没有重新解析其消费者时，仍需按现有机制更新相关文件，或完整重建。

### 真实项目回放

使用上轮审计冻结的同一文件清单与完整项目宏上下文：OceanBase 14,273 个文件，MAME 21,810 个文件。对比基线为上轮审计数据库（`bfe0a38` 加当时的实验改动，提取版本 23）；此次工作区起点为干净的 `bfe0a38`。没有改动源项目或其正式索引。

回放只执行提取，按真实节点 ID 去重；不包含引用解析、关系合成和正式数据库初始化，不能当作完整 init 耗时或 sync 提速数据。

| 项目 | 文件数 | 修复前节点 | 修复后节点 | 净减少 |
|---|---:|---:|---:|---:|
| OceanBase | 14,273 | 921,778 | 882,127 | 39,651 |
| MAME | 21,810 | 1,608,621 | 1,599,331 | 9,290 |

两组均无 worker 失败。原有纯宏数据头诊断仍分别为 8 个和 21 个；MAME 另有 2 个文件（`src/mame/bfm/bfm_sc4.cpp`、`src/mame/igs/goldstar.cpp`）触发现在显式报告的宏展开预算告警，诊断文件总数为 23。OceanBase 的 5,560 个伪 `TestBody` 变量被消除，真实 `TestBody` 方法由 6,245 个增至 6,327 个；include 片段中 3,419 个赋值伪变量被消除。MAME 的 `TIMER_CALLBACK_MEMBER` 伪函数/方法、4,927 个 `PORT_PLAYER` 伪变量及 105 个 `mycycles` 赋值伪变量已消除，真实回调与静态成员限定名由正向用例检查。

净减少不是被修复节点的总量：MAME 同时移除了 41,411 个旧 ID、增加了 32,121 个 ID。提高宏展开预算和修复展开词法规则补回了先前遗漏的真实类型、字段声明与静态成员定义，不以压低总节点数为目标。全量类/结构体 ID 对照中，OceanBase 无旧类型丢失；MAME 只有 4 个错误拼接名称被纠正，例如 `driver_194399_traits` 变为 `driver_1943u_traits`，对应声明位置均已校验。此前处于预算边界的 BFM 类型也已保留。

此次并发回放的提取墙钟时间分别约 296 秒、548 秒，包含测试程序写入对照数据库的时间。该回放只用于验证提取结果；端到端性能另行测量如下。

最终统计见本机实验目录 `release/benchmarks/symbol-fix-20260927/`；修复前明细在 `release/benchmarks/extraction-audit-20260926/`。回归日志、真实问题样本和兼容检查在 `release/benchmarks/extraction-fix-20260926/`。这些大型实验产物不纳入版本控制。

### OceanBase 完整 init 与 1,000 文件 sync

2026-09-27 在同机独立镜像重新测试：修复前为干净的 `bfe0a38`（提取版本 22），修复后为本次变更（版本 24）。两版均从空数据库初始化，再应用同一批真实分支差异的 1,000 个 C/C++ 文件，载荷为 21,908,222 字节。Windows、Node 24.11.1、`--liftoff-only`、原生 SQLite 和 Rust 扫描器，默认并发；两版顺序运行。

| 场景 | 修复前 | 修复后 | 耗时减少 |
|---|---:|---:|---:|
| 完整 init | 425.341 秒 | 398.506 秒 | 6.3% |
| 1,000 文件 sync | 332.714 秒 | 241.842 秒 | 27.3% |
| 无变更 sync | 0.734 秒 | 0.635 秒 | 0.099 秒 |

sync 的初次写图由 61.107 秒降至 43.152 秒；遗留待解析引用清理及关系合成由 106.512 秒降至 44.264 秒，其中引用批处理减少约 51.9 秒。直接变更均为 1,000 文件，另有 87 / 86 个调用方触发补偿处理。两版均完成、无文件错误、待处理引用为 0，最后无变更检查通过。

每项为单轮测量，未清空操作系统缓存。此前另一实验版曾测得 sync 220.865 秒，包含当时其他未提交改动；当前结果比该历史记录慢约 9.5%，不能称为优于全部实验版本。原始数据与完整阶段报告保存在本机 `release/benchmarks/oceanbase-init-sync-20260927/`。

## 已有索引更新

旧索引会显示需要重建的版本提示。安装包含本修复的版本后，在项目目录执行：

```powershell
codegraph index -f
```

普通 sync 只更新处理过的文件，不能一次清理所有未修改文件中的旧伪节点。重建后，搜索到的伪节点会减少，静态成员查询会返回正确的类限定名；真实的字段、宏、声明和宏生成方法仍属于索引范围。
