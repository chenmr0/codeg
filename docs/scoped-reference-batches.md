# 密集引用 sync 栈溢出修复

## 问题及修复范围

原 `QueryBuilder.getUnresolvedReferencesByFiles()` 每次限制 500 个文件参数，却用 `rows.push(...chunkRows)` 展开不限数量的结果。单文件或一个文件组返回十几万条引用即可超过 V8 调用参数容量。Linux 现场 `failedPhase=loadRefsMs`、225 万 pending 引用与本地 501 文件 / 15 万调用的实际 sync 复现相符；不需要 14GB 数据库才能触发。

本轮不修改解析器、Rust 扫描、忽略规则、引用匹配策略、数据库 schema、提取版本或 WAL 策略。

- 兼容 API 改为循环追加，避免同一错误继续影响外部调用；它仍返回完整数组，不承诺内存有界。
- sync 的 changed、删除目标恢复引用、co-importer 回退三个装载入口不再使用该完整数组 API。
- 新入口 `ReferenceResolver.resolveFilesAndPersist()` 返回处理条数，不收集全量解析结果或边。
- 默认最多 10,000 条/批，小任务仍在一个批次完成；无需环境变量开启。该默认值经下述三档对比后选定，原始 5,000 档数据保留为历史对照。

## 分页及恢复保证

1. 去重文件列表，按最多 500 个 SQL 参数分组；每组只读取 count 和 max(id)，不缓存引用对象。没有 pending 时通过索引上的 `LIMIT 1` 直接返回，避免重扫恢复日志文件的历史失败引用。
2. 利用现有 `idx_unresolved_file_path`，按 SQLite 的 `(file_path BINARY, id)` 顺序读取。先用 `file_path=? AND id>?` 完成上一页所在文件，再读取较大的文件路径。避免单一 OR 游标反复扫描同一个巨大文件，也不使用全组 `ORDER BY id` 的临时排序。
3. SQL `LIMIT` 限制返回条数，max(id) 固定本阶段的上界；不使用清理引用后会漏读的 OFFSET。
4. 每批复用现有文件/名称/源码缓存，解析、写边后按引用 rowId 删除成功项、把未匹配项标为 failed。比较实际更新/删除条数与本批大小；异常不会悄悄推进游标或清除恢复日志。**不按每页全表 COUNT 校验**。
5. 已完成的批次保持落库，未完成批次仍可恢复。批间让出事件循环，不持有 SQLite 读事务或遍历器。保持原先幂等写边、rowId 清理和整个 sync 成功后才清除 journal 的机制。
6. 新分页 SQL 仅按形状和参数个数缓存，既减少重复 prepare，也避免 sql.js 把每一页的新语句保留至连接关闭。

内存上界针对本次装载的引用、归一化引用、本批解析结果及边；项目级名称集合、已有解析缓存、非 C/C++ 的延迟链式调用队列及 sql.js 本身的内存数据库不在这个上界内。不能把它描述为“整个进程只占 10,000 条引用的内存”。

## 验证

新增 `__tests__/scoped-reference-batches.test.ts` 覆盖：

- 原始 501 文件 / 150,000 调用的真实 sync，不再调用完整装载 API，调用边全部存在，pending/journal 清零。
- 单文件 150,001 引用；删除和标记 failed 混合发生，无漏读、重复读取。
- 超过 500 文件、重复路径、空文件组、Unicode/引号路径、固定高水位。
- EXPLAIN 检查现有索引 seek，不产生临时排序；sql.js 回退及语句缓存。
- C++ 继承/重载、TypeScript import/继承在每页 1 条的最严边界下，图与完整装载对照一致。
- 解析缓存只装载一次，进度单调；全失败批次继续处理，清理 no-op 必须报错。
- 真正的 sync 中途失败后关闭重开数据库，利用 journal 续跑，不重新解析已存文件，重复调用全部保留。

相关解析与 sync 回归还覆盖删除、恢复、改名、图重连、宏扫描、无变更同步等。Windows Vitest 默认会过滤父进程的 `--liftoff-only`；大型旧解析套件曾遇到 WASM 编译 OOM。验证时明确传入 fork 的 `execArgv: ['--liftoff-only']`，不改变产品的运行配置。

本次验证共 18 个文件、296 项通过（其中新增 14 项）。sql.js 测试显式禁用测试环境的 fetch，让现有 Emscripten 包通过本地 fs 读取 WASM，避免 Node fetch 不支持 Windows 文件路径的测试装载问题；不改产品适配器。

## 可重复性能测试

```sh
npm run build
node scripts/benchmark-scoped-references.cjs 200000 3 200
node scripts/benchmark-scoped-references.cjs 1000000 1 1000
node scripts/benchmark-scoped-references.cjs 2250000 1 5000 paged
```

脚本只创建、清理自己拥有的临时数据库和源码，不接受真实项目数据库路径。每种模式独立进程，交错顺序；生成 25% 可解析调用和 75% 缺失目标，比较调用边及失败引用的完整哈希。`legacy` 是**仅循环追加、不分页的可运行修复**，不是必定崩溃的原版本。

`resolutionMs` 包含查询、解析、入库及清理，不包含建库/数据生成/验证；不是完整 CLI sync 耗时。`processPeakRssMiB` 是截至引用处理结束时读取的进程高水位，包含两种模式相同的数据准备过程，不含后续验证。225 万条仅运行 paged 时，`parity=not-compared` 表示没有对照运行，不是发现差异；该模式仍验证准确计数与 pending 清零。

分页增加查询及事务次数，可能略慢；它的主要目的为消除崩溃并降低引用处理的峰值内存，不保证所有环境加速。基准结果需结合 Linux 实机验收，不能外推成 17 分钟整条同步的完成时间。

### 本机测量（Windows，Node 24.11.1）

对照为同一构建中的兼容完整数组 API（已移除危险展开）与正式分页入口；20 万取交错三轮中位数，100 万为一轮对照。

| 引用 / 文件 | 完整装载耗时 | 分页耗时 | 耗时变化 | 完整装载峰值 RSS | 分页峰值 RSS |
|---|---:|---:|---:|---:|---:|
| 200,000 / 200 | 2.026s | 2.121s | +4.7% | 456MiB | 210MiB |
| 1,000,000 / 1,000 | 12.081s | 13.082s | +8.3% | 1,465MiB | 281MiB |

两组边和失败引用的完整哈希均一致，pending 清零。20 万结果为 50,000 调用边 / 150,000 failed；100 万为 250,000 调用边 / 750,000 failed。这些 failed 是合成输入故意引用不存在的目标，不是批处理失败或漏读。

- 20 万哈希：`ae04e91ab163e0154c520304cc035a2604b5bae785d7307b51d7ed4848c185df`
- 100 万哈希：`8f0d29601d8006f5f70c89283e234b7c857db087f2bab9b25f13061429654bbc`

内存代价显著降低，但本机确实测到了少量耗时增加，不能对外宣称“零性能成本”。

225 万引用 / 5,000 文件的最终分页压力测试：27.941s，450 批，最大批次 5,000，进程峰值 RSS 290MiB；生成 562,500 条调用边，1,687,500 条预期 failed，pending 为 0。只执行分页模式，没有把它标为与完整装载做过差分。结果哈希为 `277594e02886cbba7ead6c6f9a8f6356061ec3d3af03dd290c9cdeedfbfc3254`。

小范围 100 引用 / 20 文件交错三轮：完整装载 12.120ms，分页 12.823ms，中位数差约 0.70ms；两种模式进程峰值均约 62MiB，完整图哈希一致。该数据只说明本机小批任务的新增绝对开销很小，不等于所有小仓完全零开销。

### 5,000 / 10,000 / 20,000 批大小实验

基准新增 `batches` 模式；每档独立进程、重新构造同样的数据，每三轮轮换先后顺序。
为保持比较独立于产品策略，仅在基准子进程内临时提高导出常量的校验上限，并显式传入批大小；分页、匹配、缓存、入库和清理算法不替换，不编辑 source/dist 文件。以下实验时产品默认为 5,000；验收候选包现已调整为 10,000。普通 `paged` 模式跟随当前构建默认，`batches` 模式始终显式比较三档。

```sh
node scripts/benchmark-scoped-references.cjs 200000 3 200 batches release/batch-sizes-200k.json
node scripts/benchmark-scoped-references.cjs 1000000 3 1000 batches release/batch-sizes-1m.json
node scripts/benchmark-scoped-references.cjs 2250000 1 5000 batches release/batch-sizes-2250k.json
```

最后一个参数可省略；提供时保存完整结果和汇总到一个新 JSON 文件，不覆盖已有文件。每档都校验准确的调用边数、failed 数、pending 清零和完整图哈希。这里的 failed 仍是故意构造的缺失目标。

20 万引用 / 200 文件，三轮中位数：

| 批大小 | 引用处理耗时 | 相对 5,000 | 进程峰值 RSS | 相对 5,000 |
|---:|---:|---:|---:|---:|
| 5,000 | 2.164s | 基准 | 205MiB | 基准 |
| 10,000 | 2.015s | -6.9% | 228MiB | +11.2% |
| 20,000 | 2.075s | -4.1% | 292MiB | +42.3% |

三档结果哈希相同，实际批数为 40 / 20 / 10。这个场景不支持“批越大越快”的结论；轮次仅三轮，不能把中位数差异当作所有环境的确定收益。

100 万引用 / 1,000 文件，三轮中位数：

| 批大小 | 引用处理耗时 | 相对 5,000 | 进程峰值 RSS | 相对 5,000 |
|---:|---:|---:|---:|---:|
| 5,000 | 13.118s | 基准 | 280MiB | 基准 |
| 10,000 | 12.169s | -7.2% | 291MiB | +4.1% |
| 20,000 | 11.890s | -9.4% | 324MiB | +15.8% |

三档图哈希相同，pending 清零；实际批数为 200 / 100 / 50。10,000 已获得大部分收益；20,000 相比 10,000 额外节省约 0.278s（2.3%），峰值多约 32.5MiB（11.2%）。这里只证明合成场景下的性能/内存权衡，未改产品默认，也未把该结论外推为真实 Linux 原库总耗时。

225 万引用 / 5,000 文件，每档一轮压力核验（不是三轮中位数）：

| 批大小 | 引用处理耗时 | 进程峰值 RSS | 实际批数 |
|---:|---:|---:|---:|
| 5,000 | 28.317s | 292MiB | 450 |
| 10,000 | 27.324s | 298MiB | 230 |
| 20,000 | 27.191s | 335MiB | 120 |

三档均为 pending=0、562,500 条调用边、1,687,500 条预期 failed，完整结果哈希相同。500 文件参数分组各自有尾批，所以批数不一定等于全局引用数除以批大小的上取整。

本机结论：10,000 是更均衡的候选。它在 20 万/100 万场景分别较 5,000 快约 6.9%/7.2%，峰值多约 23MiB/12MiB；20,000 在 20 万场景反而比 10,000 慢，在 100 万场景额外快 2.3%，225 万单轮只快约 0.5%（0.132s，不能排除测量噪声），却额外占用约 33–64MiB 的峰值内存。不能从这些合成 Windows 样本断言所有真实项目/Node 版本的最优批大小，Linux 原库还需验证。根据用户确认，候选包默认/上限现为 **10,000**；全量解析原有 5,000 批大小、WAL 策略均未改动。

本次原始记录在工作树 `release/batch-sizes-200k-20260907.json`、`release/batch-sizes-1m-20260907.json`、`release/batch-sizes-2250k-20260907.json`；共 21 次独立进程测量，分别采用 3/3/1 轮，测试脚本自动清理自建临时数据。

## 升级验收

不需要重新 init 或数据库迁移。使用包含本次构建的安装包，在确认没有另一写者运行后执行 `codegraph sync -v`，让原库继续未完成工作。不要删除 WAL 或恢复日志。

changed 阶段日志新增 `plannedRefs`、`batches`、`maxBatchRefs`；正常完成时 `refs=plannedRefs`，`maxBatchRefs<=10000`，`complete=true`。失败阶段保留逐批累计统计。整个 sync 成功后再确认 pending/journal、关键调用边和符号；其他已有解析错误不由本修复自动消除。

风险边界：分批持久化时机与显式文件/行顺序不同于旧无 ORDER BY 查询；已经做继承、重载、import 及恢复的差分回归，但不声称穷尽所有语言/框架。无新表/索引构建成本；WAL 高水位和大库写入速度作为独立事项，不能靠本修复保证解决。
