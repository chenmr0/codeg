## 目标与待验证假设

解释当前原生图为何可能比社区图查询更慢、有效源码更少，并区分四类原因：

1. **关系错误**：同名兜底、宏/变量混淆、作用域或翻译单元可见性不足，把引用绑定到错误实体。
2. **正确关系的过度消费**：通用宏、常量、基础类型和重复发生点虽然真实，对具体需求的区分度却低，占用探索名额或源码预算。
3. **读取与执行成本**：先全量读边、构造邻居，再按节点或输出预算裁剪；SQL 计划、缓存失效和初始化也可能放大成本。
4. **维护放大**：错误中心节点制造虚假依赖，高入度目标替换触发大量入边重连，sync 后首查再次支付全图工作。

不预设新增边大部分错误，也不预设减少边数一定改善结果。官方解析器亦非编译器真值。目标是用独立源码证据和分离变量的工具级测量，确认问题所在，再形成通用修复提案。

## 硬约束

- 初始审计阶段不修改产品；2026-11-05用户批准进入分阶段通用修复。第一阶段只改BFS节点预取；第二阶段获准修C/C++绑定、证据失效和必要的头文件识别，提取版本40→41，schema不变。两阶段均不改Explore排序、选区或默认预算；诊断及原始证据仍留在独立目录。
- 不按 OceanBase、TTL、DTL 或具体符号名称添加排除表、规则或评分特殊处理。
- 不按 `degree > N` 全局删边，不一律删除 `references`，不一律拒绝合法函数指针/可调用变量。
- 保留 C/C++ 增强、批量工具、旧索引和日志。需要写数据库的 sync 测量只作用于新副本。
- 对照必须使用相同 query、maxFiles、源码预算和连接配置；不得缩减必要输出或关闭正确性检查制造速度收益。

### P0：先冻结证据条件

1. 核验本机原生/官方旧图、源码快照及当前运行时，记录实际可读路径和来源。
2. 旧库以真正只读方式打开；只有确认无未合并 WAL、快照稳定时才使用 immutable。不得对活跃库错误使用 immutable。
3. 只读分析前后检查主库/journal/有效 WAL、源码与运行时；SHM状态单列。避免让打开 SDK 的行为触发自动 sync、迁移或重建。
4. 对重统计和性能实验串行执行，记录预检读取带来的页缓存预热；新进程首查不等于冷盘。
5. 如果确切输入无法获得，完成独立可验证部分，并把受阻项目留在状态表，不擅自替换版本。

产物：输入清单、冻结哈希、运行协议、查询集合及已知限制。

### P1：查清图中保存的究竟是什么

分别统计原始边发生次数、唯一 `(source,target,kind)`、声明定义归一后的逻辑关系、唯一来源函数数和文件数。

分层维度包括：边类型、`resolvedBy`、规则置信度、源/目标节点类型、语言族、同/跨文件、生产/测试路径、入度/出度。先采用有界查询发现候选，再安排确有必要的单次全图统计，避免反复全表扫描。

`confidence=0.9`只是规则给分，不作为90%正确率使用。抽样规则与随机种子必须在查看工具输出前冻结。

高连接节点审计与普通节点对照并行设计；不能仅根据高连接样本推算全图错误率。样本选择使用预先记录的规则和种子，不只挑已知失败的符号。

每条人工复核样本记录：引用点原文、作用域、候选目标与定义、选择理由、include/宏/声明证据、是否可证明可见，以及正确/错误/不确定结论。预处理配置不明时保留不确定，不强行算成正确或错误。

重点检查：

- 生产文件是否引用不可见的测试局部变量或错误 owner；
- 宏、普通变量、函数指针、重载及可调用对象是否被混淆；
- C/C++ 互通的语言评分是否压过正确的可见性证据；
- 签名类型、函数体引用、宏展开依赖和运行调用是否有足够的来源区别；
- 重复发生点、声明定义桥和真正新增调用拓扑是否被混为一谈。

产物：图统计、节点分布、分层样本表、可复核错误案例、未知项。必要时用通用小型源码在当前原生/官方提取器上复现，不能仅把历史库缺陷推断为当前提取结果。

### P2：定位真实 Explore 的读取与候选成本

沿实际 MCP ToolHandler → upstream 适配器 → 查询/遍历路径测量；不得用原生 `contextBuilder` 的耗时替代。

互斥阶段至少覆盖：初始化/词表、图统计、词法检索、BFS与邻居读取、子图补边、身份归并与签名证据、Flow、文件分配、源码核验与渲染。嵌套 API inclusive 时间不可相加，另列未归因余项。

诊断开关须保持正文SHA一致，并单列仪表开销。未归因部分超过总耗时10%时继续定位，或明确保留该边界，不宣布已找到全部主因。

同时记录：SQL次数与返回行、唯一邻居数、重复候选数、节点物化数、进入/退出各级预算的数量、最终用到的关系与源码行。重点确认“读取几十万、使用几十条”发生在哪一步，而非只看最终工具输出大小。

对目标记录：未检索到、未正确解析、未进入BFS、全局/单文件裁剪、文件排序/门槛排除、源码窗口不足、源码漂移省略。明确具名目标和附带上下文的评分分母。

性能条件分为同进程首次、第二次、外部提交后首查；生产PRAGMA统一。错误边比例不能由耗时反推，源码覆盖不足也不能仅凭边数归因。

### P3：分离变量，不同时修改多个层次

在冻结图和查询上，按审计结果选择最小、可解释的干预：

- 原始关系视图作为基线；
- 仅修正或排除有源码证据证明错误的绑定，保留未改关系；
- 完整事实保留，仅调整默认探索对特定低信息量关系的有界读取/扩展；
- 只改变执行方式、要求完整结果及顺序一致的SQL/缓存对照。

每一项先单独比较，再决定是否需要组合。临时适配不得污染产品构建或旧数据库；恢复后做哈希终核。禁止把“删除全部 references 后变好”解释成所有 references 都是错误边。

记录核心实现逐行覆盖、完整目标次数、无关输出、总字符、耗时、读取行数、内存峰值与异常；查询/目标重复数单列。变化若只改善名称/声明命中，不能称为主体改善。

### P4：在新副本中测 sync 维护放大

固定触发矩阵：无变更sync、普通调用方正文编辑、高入度目标正文编辑、目标前移一行、签名/重命名、目标删除、宏证据变化；另设普通度数目标作对照。

记录 retain/snapshot/rewire 路径、扫描/恢复的入边、删除/插入边数、pending解析量、重新提取文件数、各阶段时间、WAL字节与发布成本。高扇入worker只是执行位置变化，不能当作工作量消失。

每次同时记录 sync 返回时间与随后首次/第二次 Explore：词表和聚合重建可能把成本推迟到查询。native增量、portable重建和WASM保存分别报告，不混用口径。

验证编辑生效后的关系正确性与完整性，再恢复副本到可核验状态；不能只验速度。实际源码编辑必须是独立副本中的可逆、预先定义修改。

每个触发场景从相同冻结副本开始，保存修改补丁；与相同修改状态下的独立重建核对关系。没有完成此正确性核验时，维护计时只能作为观察记录，不作为优化验收结论。

### P5：讨论结果后再决定产品修复

结论按证据级别列出：源码机制、单因素因果、重复测量、尚未验证。优先处理已证错误绑定与无必要读取，再讨论关系用途/可信度投影，最后才考虑窗口和持久化布局。

对正确的高连接事实，考虑聚合、按文件过滤、计数和分页，而不是因模型上下文有限就全局删除。任何解析门槛、关系权重或预算规则都必须通过独立仓库及保留的函数指针、宏、重载、声明定义等反例。

## 验收与停止条件

- 没有匹配的源码/索引/构建身份，不发布跨版本性能或召回结论。
- 有超时、取消、缺臂、源码错配、输出截断或计时重叠，明确判为不完整记录，不包装为成功。
- 图质量样本中不确定与已证明错误分列；局部错误例不能代表总体错误率。
- 单因素对照出现其他主体回退必须列明，不靠总量提升掩盖；旧日志始终保留。
- 达到预先规定的证据条件后收敛，不为追分继续增加查询或规则；新增问题另立条目。
- 不受阻的审计继续执行。需要外部输入的项目记录条件和已完成工作，避免无意义重复下载、重建或轮询。
- 状态统一使用：未开始、进行中、已验收、输入受限、未通过。每次更新分别列事实、解释、未验证假设、证据位置与下一动作；旧快照审计完成不代表当前版本全仓结论完成。
