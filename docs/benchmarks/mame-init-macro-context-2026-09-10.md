## 本阶段修复

`TreeSitterExtractor.buildDeclarationMacroRecoverySource` 原本对每一个声明宏调用向上寻找命名空间、类、结构体等容器，并重新获取 `body.namedChildren`，遍历全部子节点寻找调用之前最后一个访问权限标签。大型命名空间或类中，宏调用数与声明数同时增加，形成重复扫描。

`goldstar.cpp` 有 3,045 个宏调用位置。Node CPU profiler 的一次 43.153 秒提取中，恢复源码构造的计时为 31.379 秒；采样调用栈中 `namedChildren` 的包含耗时约 25.063 秒，伴随 WASM 子节点遍历和大量 JS 节点包装对象创建。这是算法热点，改用 Rust 之前也可以消除。

修复保持原来的源文件裁剪规则：

- 每个容器只保留一次起止边界和模板头，只扫描一次直接子节点，将访问权限位置记录为行号数组。
- 后续调用按行号二分查找最后一个访问权限标签，包含同一行有多个标签的情况。
- 使用树内唯一的 `SyntaxNode.id` 作为键，因为 `parent` 查询可能创建不同 JS 包装对象。
- 缓存只存在于本次恢复调用中，只保留行号；没有跨文件或跨语法树的 AST 缓存。函数体续行、注释、字符串处理和生成节点合并规则不变。

这将同一容器下重复的“宏调用数 × 子节点数”扫描，变为一次子节点扫描及各调用的权限位置查找。祖先遍历深度限制保持 128。

## Rust 是否适合我们的场景

### 社区 Rust 实际加速什么

社区 `codegraph-kernel` 是 napi-rs 原生模块。`src/lib.rs::extract_file` 在 Rust 内完成 tree-sitter 解析和 AST 提取，每文件返回 meta、nodes、edges、refs、arena 五个扁平缓冲区。并行仍由 JS worker 池负责；原始缓冲区可一直传到 store worker 再解码，减少 AST 访问时的 JS/WASM 往返、对象创建和跨 worker 数据传递。

我们的 `codegraph-scan`、`codegraph-macros` 已经使用 Rust，但主要做文件和宏上下文扫描，不包含上述原生 AST 提取。此前 MAME 完整实验中宏扫描约 6–7 秒，无法解释数百秒的提取和引用解析耗时。此前社区 353.557 秒的完整基准也没有启用原生 kernel：当时本地没有对应二进制。因此此前社区更快不能归因于 Rust。

### 已实际编译，而非仅阅读源码

使用已有 Rust 1.98.1 工具链，将社区 crate 复制到实验目录，以原 `Cargo.lock`、release 配置、4 个编译任务构建；缺少的依赖通过 Cargo 下载，没有修改社区源码。Windows x64 原生模块约 35.5 MB。本阶段产品代码没有新增 native kernel 依赖，也没有启用实验开关。

先从我们已索引的 21,428 个 C/C++ 文件按路径排序等距取 256 个，再加入上表六个热点文件，共 262 个。语言标签沿用我们数据库中的分类，应用社区 `EXTRACTORS[language].preParse` 后调用原生内核，因此也包含社区默认扩展名检测未必收录的文件。

| 抽样指标 | 结果 |
| --- | ---: |
| 原生提取成功 | 105 / 262 |
| 默认回退 WASM | 157 / 262 |
| 成功文件与社区自己的 WASM 结果相同 | 105 / 105 |
| 成功文件与我们的结果存在差异 | 102 / 105 |

结果比较包括节点全部业务字段、边、未解析引用及错误多重集，排除 `updatedAt`，忽略对象键及集合顺序。成功的 105 个文件，原生路径包含预处理和解码共约 0.606 秒，社区 WASM 约 0.977 秒，约 1.61 倍；这是同一 Node v24.11.1、`--liftoff-only` 下的单次小样本对照，不能代表完整 init。其余 157 个文件仅失败前的原生解析就另需约 2.278 秒，之后仍需 WASM，说明默认尝试原生也有回退成本。没有用语义不同的 fork 耗时来宣称原生加速倍数。

### 全部 C/C++ 文件的默认回退检查

进一步对上述 21,428 个文件逐个应用社区预处理和原生提取，未打开 `CODEGRAPH_KERNEL_CCPP_ERROR_EXTRACT`：

| 指标 | 结果 |
| --- | ---: |
| 原生成功 | 8,799（41.06%） |
| 返回 `defer:`，交由 WASM 处理 | 12,629（58.94%） |
| 其他错误 | 0 |
| 原生成功文件字节数 / 总字节数 | 155,962,021 / 431,856,010（36.11%） |

将成功文件集合与第三阶段记录的 C/C++ 慢文件匹配：487 个单次提取超过 250 ms 的文件，逐文件耗时累计 604.492 秒，其中可走社区原生路径的文件累计 75.792 秒，仅占 **12.54%**。这是并行 worker 的逐文件墙钟累计，既不是 CPU 时间，也不是完整 init 的时间占比。它说明当前社区原生路径对主要慢文件覆盖有限，不能据此给整个 init 套用原生成功样本的加速倍数。

抽样记录的回退原因可直接对应社区 `codegraph-kernel/src/ccpp/mod.rs`：默认 `tree.root_node().has_error()` 就返回 `defer:`。社区明确将 WASM 的错误恢复视为标准行为；直接强制开启错误树原生提取会绕过这个一致性保护，不作为本次优化方案。

### 直接移植还存在的语义差异

- 原生 contract 的节点类型没有我们的 `macro`。例如 `src/devices/bus/a2bus/corvfdc02.h`，我们的输出包含头文件宏和声明宏恢复出的 `A2BUS_CORVFDC02` 变量，社区原生结果没有这些节点。
- 不仅节点数量不同，声明标记、签名及引用收集规则也有差异。例如 `AES_256_CBC.h` 原生和社区各 18 个节点，我们为 26 个；我们的未解析引用还多出 489 条。不能只补宏节点就认定覆盖一致。
- C grammar 不一致：社区原生与社区 WASM 都是 ABI 15、363 个节点类型，我们当前 C WASM 为 ABI 14、351 个节点类型。C++ 的 ABI、节点类型表和字段表检查均一致，但这并不替代提取结果的业务字段比对。

### 建议的采用顺序

Rust 对原生 AST 遍历、减少中间对象与跨 worker 传递有帮助，值得继续评估；当前不宜直接默认接入社区提取器。

1. 继续消除已经确认的重复扫描。本次容器缓存无需新增编译或分发依赖，便能将相关恢复源码构造降到毫秒级。
2. 若启动原生提取适配，先对齐 grammar、节点类型、声明元数据和引用规则，用我们的结果作为一致性标准，采用可选验证模式及逐文件回退。
3. 优先解决 MAME 宏密集文件的预处理、声明宏恢复和错误树语义。只支持当前能成功的普通文件，难以覆盖主要热点。
4. 语义对齐后，再评估社区“每文件扁平缓冲区 → store worker”的数据传递方式，并以完整 init、峰值内存和全图一致性决定是否默认启用。

引用解析及关系合成也占据大量时间；社区 AST 原生模块不会自动加速我们的这两部分。本阶段不做全库 Rust 重写。
