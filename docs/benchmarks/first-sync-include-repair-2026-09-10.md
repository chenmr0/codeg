# C/C++ 首次 sync 的 include 修复优化

日期：2026-09-10。基线：`8237b14`（生产代码与 `85b3045` 相同，前者仅增加上一阶段验收报告）。环境：Windows，Node.js 24.11.1。

本阶段修复了新索引首次 sync 无条件重试全部失败 include 的问题。MAME 首次无变化 sync 的平均耗时从 **14.966 秒降至 9.266 秒（−38.1%）**，OceanBase 从 **9.055 秒降至 6.059 秒（−33.1%）**。两仓库共完成 36 次 sync，四组完整图对比没有内容差异。普通增量 sync 未观察到明确退化；小幅正负变化和样本限制见下表。

## 原因与修改

`repairLegacyCppIncludes()` 是首次 sync 执行的兼容性修复，使用 `repair:cpp-include-targets-v1` 元数据记录完成状态。它原本会处理两类历史问题：

1. 有原始引用标记、却连到非文件节点的 C/C++ 导入边。
2. 失败 include 的旧尾部索引键，例如把 `dir/api.h` 截成 `h`。

第二部分此前无条件把所有失败 C/C++ include 改回 pending，连新索引中已经正确保存为 `api.h` 的记录也会重试。因此，即使源文件完全没有变化，新索引首次 sync 仍会进入引用解析及后续维护流程。

修改后，仅当保存的 `name_tail` 不等于 `reference_name.split('/').pop()` 时，才把失败 include 转回 pending。比较规则与现有两个失败引用写入入口完全一致，保留大小写和无扩展名头文件。错误成功边的修复逻辑、事务和完成标记保持原样。

这不是删除失败引用：正确记录继续保留，缺失头文件后来出现时仍由普通 sync 恢复。旧键继续修复；提交修复标记后中断，下一次 sync 仍能处理已经留下的 pending 引用；标记写入失败会回滚整次修复。

生产改动仅位于 `src/db/queries.ts` 的上述方法。冻结构建的运行时 JavaScript 对比仅发现 `db/queries.js` 变化，屏蔽该方法后文件内容相同。没有新增数据库索引、修改 schema 或版本，也没有修改 init、解析规则和常规引用写入路径。

## 测量方法与范围

- 实际源目录为 `D:/c_proj/mame` 和 `D:/c_proj/oceanbase`。首次 sync 使用源目录只读扫描，数据库写入工作区内的独立副本。
- 从未执行此项兼容性修复的完整 init 数据库准备副本，计时前验证每个已索引源文件的内容哈希与种子一致。两仓库种子的失败 include 尾部键均已正确。
- 每个仓库按 before、after、after、before 顺序测试四份独立数据库；每份执行首次 sync 和两次后续无变化 sync。每个版本得到 2 个首次样本、4 个后续样本。
- 每次调用均启动新的 Node 进程。计时为 SDK 完整 `await sync()` 的耗时，构造/打开数据库另计；没有使用只覆盖部分阶段的 `SyncResult.durationMs`。
- 语义编辑在工作区内的项目镜像进行：添加函数与调用、改名并更新调用、恢复原文件。每个场景每个版本一次，交替执行版本顺序，共 12 次。编辑后检查目标调用边及旧符号清理，最终恢复镜像源文件。
- 总计：24 次无变化 sync，加 12 次语义编辑 sync，均完成且没有文件错误或残留 pending 引用。

首次 sync 种子规模：

| 项目 | 文件 | 节点 | 边 | 失败引用 | 其中失败 include | 涉及文件 |
|---|---:|---:|---:|---:|---:|---:|
| MAME | 23,381 | 1,614,526 | 8,613,227 | 1,054,432 | 12,371 | 4,597 |
| OceanBase | 14,347 | 926,980 | 5,558,130 | 1,220,338 | 4,792 | 2,056 |

MAME 的语义编辑沿用上一阶段 23,380 文件的镜像种子；两个版本使用相同种子。它与本次首次 sync 种子相差 `3rdparty/genie/src/host/scripts.c`：该文件既受 Git 跟踪，又匹配嵌套 ignore 规则，历史 Git/文件遍历路径的选择结果不同。首次与语义测试分别做版本对照，不把两种扫描范围混为一组。OceanBase 两类测试均为 14,347 文件。上一阶段完整 init 对照见 [引用解析 init/sync 验收](resolution-init-sync-acceptance-2026-09-10.md)。

## 耗时结果

单位：秒。首次及后续无变化结果为各自样本的算术平均值。

| 项目 / 场景 | 修复前 | 修复后 | 变化 |
|---|---:|---:|---:|
| MAME：首次无变化 sync，2 次/版本 | 14.966 | 9.266 | −38.1% |
| OceanBase：首次无变化 sync，2 次/版本 | 9.055 | 6.059 | −33.1% |
| MAME：后续无变化 sync，4 次/版本 | 2.415 | 2.378 | −1.5% |
| OceanBase：后续无变化 sync，4 次/版本 | 0.296 | 0.302 | +5.5 毫秒 |
| MAME：添加函数及调用，1 次/版本 | 17.878 | 17.506 | −2.1% |
| MAME：改名及更新调用，1 次/版本 | 11.355 | 11.321 | −0.3% |
| MAME：恢复文件，1 次/版本 | 11.424 | 11.620 | +1.7% |
| OceanBase：添加函数及调用，1 次/版本 | 5.748 | 5.575 | −3.0% |
| OceanBase：改名及更新调用，1 次/版本 | 3.918 | 4.005 | +2.2% |
| OceanBase：恢复文件，1 次/版本 | 3.985 | 3.909 | −1.9% |

首次样本原始值：

| 项目 | 修复前两次 | 修复后两次 |
|---|---|---|
| MAME | 14.297 / 15.634 | 9.257 / 9.276 |
| OceanBase | 9.074 / 9.036 | 6.044 / 6.074 |

首次 sync 的改进在两轮、两个仓库上方向一致，日志也能直接解释原因。普通 sync 的微小差异不应视为稳定提升；语义场景每种只有一个样本，也不足以据此认定百分之一到二的稳定退化。已经完成标记的普通 sync 仍然走原来的立即返回路径。

首次 sync 的采样峰值 RSS：MAME 从 389.5 MiB 降至 347.7 MiB，OceanBase 从 285.7 MiB 降至 261.2 MiB。语义场景的峰值有小幅正负变化，没有据此提出常规 sync 内存收益结论。

### 日志归因

| 首轮基线首次 sync | MAME | OceanBase |
|---|---:|---:|
| 被重新解析的文件 | 4,597 | 2,056 |
| 被重新解析的失败 include | 12,371 | 4,792 |
| 新解析成功引用 / 新边 | 0 / 0 | 0 / 0 |
| 此次引用处理总耗时 | 4.656 秒 | 2.660 秒 |
| 其中实际匹配 | 3.911 秒 | 2.127 秒 |

修复后首次 sync 的 `changedRefsMs` 为 0，失败引用重试和图合成阶段也不再因这些正确记录而启动。整次 sync 的收益还包含避免这些无效重试带出的后续工作及运行波动，不等同于表内某一个阶段耗时。

首次 sync 仍需约 9.3 / 6.1 秒：兼容性检查和首次读取较大数据库的成本仍然存在。这些是计时前准备的独立数据库副本，没有刻意清空系统文件缓存，不能把结果解释为严格冷磁盘测试，也不能直接等同于刚完成 init、缓存仍热时的耗时。

## 正确性验证

新增测试在修复前有 3 个预期失败；修复后相关 8 个测试文件的 **113 项测试全部通过**，`npm run build` 通过。覆盖内容包括：

- C 和 C++ 新索引首次空 sync 不调用文件引用解析，失败引用整行保持不变。
- 首次修复完成后，新增先前缺失的嵌套头文件可恢复正确文件导入边，其余缺失引用继续保留。
- 同文件内旧键与正确键混合、无扩展名头文件，只重试旧键。
- 修复标记已提交、解析前中断后的恢复，以及标记失败时错误边与失败引用的事务回滚。
- 现有跨文件恢复、重试过滤与状态、WAL 延迟、游标批处理、常规 sync 和名称查找回归。

四组完整数据库内容比较全部通过：MAME / OceanBase 各自的首轮首次 sync 结果，以及语义编辑后恢复原文件的结果。节点、文件、边及引用多重集没有增删或内容变化；边的身份、元数据及 provenance 也一致。比较忽略节点更新时间、文件索引时间和未解析引用的内部行 ID。四组均无 pending，外键检查为空，SQLite `quick_check` 为 `ok`。第二轮首次 sync 做场景和计数检查，没有再逐字段比较整库。

本阶段没有重跑完整 MAME init：运行时差异仅限由 `CodeGraph.sync()` 调用的一次性兼容方法，init 路径及其写入代码均未变化。测试夹具执行了新建索引；完整仓库 init 的耗时结论仍以链接的上一阶段报告为准，不把本次 sync 收益表述为 init 收益。

## 本阶段未采用的方案

另外做了只读 SQL 查询计划与耗时对照。错误成功边查询的替代写法仅节省少量时间；失败引用查询强制全表扫描在当前种子上较快，但尚无完整 sync 收益证明，并可能不适合 pending/failed 比例不同的旧数据库。因此本次保留原索引选择，没有强制扫描计划，也没有添加会增加 init 或日常写入维护成本的新索引。

后续如继续优化，可单独衡量一次性检查中的数据库读取，以及高扇出头文件变更触发的解析和批次调度成本。它们未包含在本次修复中。
