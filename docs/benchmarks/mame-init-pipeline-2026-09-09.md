# 第二阶段：有序解析流水线

第一阶段已提交为 `d89d718`（优化：消除 init 重复写入与提取热点并补充 MAME 验证），完整 MAME 基准为 22 分 42 秒。本阶段在这一提交上继续改进解析调度，并独立记录收益与正确性验证。

## 实现范围

- 用 `orderedParallelMap` 替代每 10 文件的整批解析屏障。最多预取 `4 × parse worker 数` 个未消费任务，空闲 worker 可处理后续文件；消费及 SQLite 提交仍严格遵循扫描顺序。
- 先校验路径、获取小型 stat 记录，再预留空间并读取源码。保留原来的每 10 文件并行 stat；不提前读入整批大文件内容。
- 初始预留为源码字节数的 16 倍、至少 32 KiB，涵盖字符串及可能的图对象膨胀。完成解析后，改为按实际字符串长度、节点/边/引用数量估算保留大小。
- 预算同时参考系统可用内存的 1/16、主线程剩余堆的 1/4，范围 32–512 MiB。系统内存沿用已有 cgroup/macOS 感知的 `memoryBudgetBytes`。超预算单文件在窗口为空时仍能执行，不因大小而丢失文件。
- 已运行任务完成时可能超出估算阈值，此时暂停新任务入队。**这是缓冲区准入预算，不是 V8/WASM 或总 RSS 的硬上限。** 文件数上限始终有效。
- 写库线程同时按 bundle 数和估算字节数背压；接到 ack 才释放其预留，避免数据转交写库线程后从预算中“消失”。解析端和写库端各自使用该预算。
- 取消时停止消费，关闭输入迭代器，丢弃迟到结果；worker 生命周期仍由现有 orchestrator 的 finally 清理。逐文件读取/解析错误继续走原诊断与重试流程，写库异常终止后续消费。
- 调度、byte 估算与队列背压之外，未改引用解析/匹配算法、WAL 阶段切换、宏恢复规则或支持文件范围。

指标新增 `parsePipeline`、`readSum`、`bufferBudgetMB`、`peakBufferedFiles`、`peakEstimatedBufferMB`。`readSum` 是并行 I/O 请求耗时累计，`parsePipeline` 是含读/解析/提交的重叠流水线墙钟，不能直接与旧版 `parseWall` 比较或把这些指标相加。

## 校准与回归

135 个真实 MAME 文件：128 个跨目录 C/C++ 样本、6 个超过 4 MB 的 m68000 生成文件、已知慢文件 `goldstar.cpp`。使用相同 8 worker 和全项目宏上下文，有序消费并计算业务结果指纹，**不包含 SQLite 写入**。

| 调度 | 时间 | 采样 RSS 峰值 | 结果 |
| --- | ---: | ---: | --- |
| 每 10 文件整批等待 | 69.786 秒 | 2.08 GiB | 基准 |
| 流水线，固定 128 MiB | 86.643 秒 | 1.39 GiB | 大文件并行度受限，未采用为高内存机器默认值 |
| 流水线，512 MiB | 64.240 秒 | 2.07 GiB | 与基准指纹一致 |

三种调度均为 19,656 节点、20,307 边、1,488,764 引用，错误数 0；SHA-256 均为 `b8dbee6839f199ef372d514b44eb0a4140e44d5e487c4d6518dd33d6a9d39bc2`（nodes 排除 updatedAt，包含 edges/refs/errors）。校准未记录全机 CPU 负载；后续全量运行发现 IDE 干扰，因此这些时间只作为参数校准观测，不外推为全库收益。

构建通过。解析流水线完成后的全量 Vitest：147 个文件，138 通过、7 失败、2 跳过；2,400 项通过、52 项失败、13 项跳过。与前一阶段旧版复现日志逐一比较 52 个失败用例名称，差集为空。随后追加写库字节背压及其 3 个测试，相关 5 文件、28 项测试全部通过。

本阶段新增 16 项回归，覆盖：慢文件与有序消费、输入/结果预算、超预算单文件、主线程堆与系统预算、稠密引用估算、迟到拒绝、取消、写库异常、空/串行窗口、真实 indexAll 的读取错误及顺序、写库 ack/失败时的背压释放。

## 全库验收

输入仍为 `D:\c_proj\mame`，数据库与锁位于工作区的新实验目录。比较对象是第一阶段的 `fork-fixed` 数据库；保留之前的构建和数据库。两阶段均使用 Node 24.11.1、`--liftoff-only`、8 个 parse worker、6 个 resolver worker；宏扫描均为相同 TS fallback。

### 排除受干扰的计时

第一轮 `fork-pipeline` 完整运行 1,523.106 秒（25 分 23 秒），提取阶段 536.081 秒。运行中按进程 CPU 增量采样，发现 WebStorm 占用约 24.18 个逻辑核，而基准进程占用约 4.04 核。引用解析等未改动阶段也明显变慢，因此不将本轮总时间或阶段时间用作性能结论。

用户选择等待 IDE 空闲后复测。22:25 左右 WebStorm 退出；22:26 的采样和复测启动前的采样确认没有同类高 CPU 占用进程。复测 `fork-pipeline-quiet` 使用同一构建，新增每 5 秒的全机及基准进程 CPU 记录；外部占用估算为两者之差，不把“IDE 已退出”直接等同于整个运行期间无干扰。

复测完整耗时 **1,150.549 秒（19 分 10.5 秒）**，相对第一阶段历史记录 1,362.136 秒减少 **15.5%**。共取得 211 次 CPU 采样，按时间加权的外部平均占用 1.98 个逻辑核，采样值 P95 为 2.90 核、最大 3.58 核，没有超过 4 核的采样窗口。定时器在同步 SQL/合成阶段可能延后；这里的“最大”是采样窗口平均占用的最大值，不能排除更短的瞬时峰值。

| 阶段 | 第一阶段历史全量 | 第二阶段空闲复测 |
| --- | ---: | ---: |
| 扫描、宏上下文、提取和写入 | 594.177 秒 | 388.008 秒 |
| 提取后二级索引与 FTS | 47.087 秒 | 48.974 秒 |

| 提取阶段采样 RSS 峰值 | 3.96 GiB | 4.55 GiB |
| 全程采样 RSS 峰值 | 12.54 GiB | 11.34 GiB |

本轮窗口为 32 文件，解析预算 512 MiB，最高结果估算 583 MiB；超出估算来自已入队任务的结果膨胀。更大的预取窗口增加了提取阶段 RSS；本改动不保证全进程内存下降。全程峰值出现在未改动的引用解析阶段，不能将本轮全程 RSS 的下降归因于解析缓冲预算。

引用解析和关系合成与第一阶段接近，历史总时间的变化集中在提取阶段。但第一阶段未记录全机 CPU，不能仅凭历史记录把提取阶段的 34.7% 降幅全部归因于代码。为进一步区分环境改善和调度收益，追加第一阶段构建的空闲提取对照：保持真实 MAME 根目录、宏扫描、8 worker、fresh store 和索引清理相同，在提取边界停止，省去未改动的引用解析与合成。

| 相同提取边界的空闲对照 | 第一阶段构建 | 第二阶段构建 |
| --- | ---: | ---: |
| 扫描、宏上下文、提取和写入 | 592.549 秒 | 388.008 秒 |
| 提取后二级索引与 FTS | 47.830 秒 | 48.974 秒 |
| 提取阶段采样 RSS 峰值 | 3.89 GiB | 4.55 GiB |

**同条件提取阶段缩短 34.5%（204.5 秒）**。对照与第一阶段原始记录的 594.177 秒也接近，支持性能改善主要来自调度的结论。代价是本轮提取阶段 RSS 峰值增加约 0.66 GiB。这里是单次前后对照，未做多轮交错重复，不能将百分比当作所有项目与硬件上的保证。

对照完整执行了 23,380 次文件写入，文件错误为 0，保存 1,614,524 节点、1,650,802 条提取边及 7,851,814 条待解析引用；后两项是引用解析前的数据。对照的清理完成总时间为 641.685 秒，输出标记 `scope=extraction-only`，**不是完整 init 基准**。其 123 次 CPU 采样的外部平均占用为 1.59 核，P95 为 2.08 核，最大为 2.57 核，无超过 4 核的采样窗口。

## 后续优先级

新流水线完整运行中，引用解析及其索引切换仍占约 609 秒（总耗时的 53%），是后续性能工作的主要目标，应分别测量候选查找/缓存、结果传输和写入，再选择优化点。本阶段保留这些算法，避免在同一提交里混入匹配行为变化。

提取端也仍有单文件热点：本轮 `goldstar.cpp` 用时 37.63 秒，其中声明宏恢复源码构造约 27.37 秒。窗口调度无法消除该文件自身的计算成本，可作为后续独立的微基准与源码优化对象。Windows 大小写路径缓存问题则应作为单独的正确性修复处理。
