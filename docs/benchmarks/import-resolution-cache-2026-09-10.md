# 减少无效节点读取与 C/C++ import 结果缓存：未采用

日期：2026-09-10。基线为 `c5cf847`，在当前优化版本上单独验证两个解析改动，没有合并 `f34ea640` 的整个实现。

**结论：撤回本次产品代码改动，只保留实验记录。当前代码仍使用 `c5cf847` 的实现，本轮实际保留的加速为 0。** 候选在单轮完整 init 对照中，MAME 少用 27.836 秒（2.8%），OceanBase 少用 9.419 秒（1.4%）；但同步结果不足以通过此前要求的“不以 sync 退化换取 init 提速”验收，且 MAME 采样峰值 RSS 增加约 0.535 GiB。没有将这些候选数据宣称为已合入收益。

依次实验了三种范围：A 同时在 init/sync 使用两项优化；B 将 import 缓存退出同步，保留语言检查快速返回；C 将两项优化均退出同步匹配。下面完整 init 测量来自 A；B 的 init 执行代码与 A 一致；C 仅做同步隔离诊断，没有重新测完整 init，因此不把 A 的速度当作 C 的实测结果。所有候选及补丁保存在本地实验目录。

## 候选修改范围

- 语言检查只有 `references`、`imports`、`instantiates` 三类引用会使用目标节点；其他类型直接返回原结果，避免没有实际检查作用的节点读取。边类型转换仍按原规则执行。
- 全量引用解析及其只读 Worker 中，C/C++ import 策略按语言、引用类型、来源文件和引用名称复用成功及失败结果。只缓存目标 ID、置信度和解析方式，每次保留当前引用的来源节点、行列和数据库行 ID；失败缓存不阻止后续名称匹配策略。
- 每个 resolver 最多保留 5,000 项、估算 4 MiB；较小的 `CODEGRAPH_RESOLVER_CACHE_SIZE` 继续生效。使用 FIFO，命中时不额外修改 Map。超预算输入正常解析但不缓存。
- 缓存加入现有 `clearCaches()` 生命周期。同步持久化入口在匹配期间暂停 import 缓存，并在正常返回或异常后恢复原策略；普通 sync 保留之前的 import 查找方式。`CODEGRAPH_NO_CPP_IMPORT_CACHE=1` 关闭全量解析的新增缓存，保留语言检查的等价快速返回。

未改变引用匹配顺序、置信度规则、失败重试范围、数据库结构、提取流水线、Worker 数量或写库批次。没有引入全量名称预取和覆盖关系全量预取。

## 完整 init 对照

环境为 Windows、Node.js 24.11.1、`--liftoff-only`，默认 8 个提取 Worker 和 6 个引用 Worker，保持相同的自动 Rust 辅助程序。源目录分别为 `D:/c_proj/mame`、`D:/c_proj/oceanbase`，源码只读。独立数据库位于当前 C 盘工作树的实验目录，**不与此前 D 盘数据库的历史总耗时混比**。

两份构建逐文件核对，运行时 JavaScript 仅 `resolution/index.js` 和新增的 `resolution/cpp-import-cache.js` 有差异，原生辅助程序也逐文件校验一致。MAME 先基线后优化版；OceanBase 先优化版后基线。四次完整运行依次执行，没有与其他基准或测试并行。

每个仓库每版一次完整 init。计时包含 SDK 初始化至完整索引结束，涵盖提取、二级索引和 FTS、引用处理、关系合成、维护及收尾；结果统计和后续图对比不计入。它不是仅提取时间，也不是 CLI 交互配置时间。单轮前后对照不能给出稳定百分比保证。

### 内存与外部负载

| 项目 | 基线采样峰值 RSS | 优化版采样峰值 RSS | 差值 |
|---|---:|---:|---:|
| MAME | 10.297 GiB | 10.831 GiB | +0.535 GiB（约 +5.2%） |
| OceanBase | 8.615 GiB | 8.584 GiB | −0.031 GiB |

MAME 引用阶段平均采样 RSS 由约 7.587 GiB 增至 7.856 GiB。这是观察到的内存代价，不能用缓存的 4 MiB 保留预算来否认；估算保留量不是 V8、Worker、临时对象或整个进程 RSS 的上限。单轮采样也不能将全部 RSS 差值精确归因于新增缓存。

引用阶段的外部 CPU 占用估算均值：MAME 基线 / 优化版为 0.907 / 0.958 核，OceanBase 为 0.857 / 0.886 核。测量前未发现此前 WebStorm 大量占用 CPU 的干扰；运行中仍按采样记录外部负载，不能排除短时波动。

## 局部归因实验

从各仓库的固定提取后数据库取四个位置各 2,000 条真实引用，共 8,000 条，每 500 条处理一次。分别比较基线、仅语言检查快速返回、仅 import 缓存、两项同时开启。每种先热身，再正序和反序各测一次，使用新的 resolver，数据库只读。

| 项目 | 基线平均 | 仅减少读取 | 仅缓存 | 两项同时开启 |
|---|---:|---:|---:|---:|
| MAME | 1.615 秒 | 1.618 秒 | 1.587 秒 | 1.464 秒 |
| OceanBase | 1.630 秒 | 1.556 秒 | 1.605 秒 | 1.546 秒 |

每个项目所有变体的完整返回结果指纹相同。样本选取、JIT、缓存和 GC 会影响小差值，单项收益不能相加；这些结果仅用于选择进入全量验收的组合。样本中的约 9% / 5% 改善不是完整 init 的提速比例。

## 为什么将缓存限定到全量解析

最初候选在 sync 中也启用了 import 缓存，完成了两项目 52 次冷进程和 28 次连续同步。图内场景断言均通过，但 MAME 两次注释修改平均慢 0.8%，头文件修改平均慢 1.1%；连续进程的 MAME 修改样本慢约 0.2%～2.2%，OceanBase 后两次语义修改慢约 2%。这些差异不足以证明普遍退化，但也不能据此宣称同步受益。

按本阶段“不能用 init 收益交换 sync 退化”的要求，第二版候选 B 关闭同步持久化入口的 import 缓存，只保留减少无效节点读取的优化。未通过增大缓存、减少重试或裁剪候选掩盖这一问题。

B 构建与已完成 init 测量的候选 A 逐文件比较，仅 `ReferenceResolver.resolveAndPersist()` 的同步入口不同。全量 init 使用的 `resolveAndPersistBatched()`、`resolveAll()`、`resolveListForAdmission()` 及辅助程序保持一致；构建校验屏蔽该同步方法后，整个运行时文件逐字节相同。因此 B 沿用上面的完整 init 数据，并用新数据库副本重新执行全部 80 次 sync。A 的数据保留在 `sync/`，B 使用 `final-sync/`；目录名是当时的实验名称，不表示最终采用，不混合计算均值。

B 和后续 C 均分别通过相关 12 个测试文件、255 项测试，包括缓存预算、不同文件/语言/引用类型隔离、原始调用位置保留、失败结果失效、同步暂停缓存及异常恢复策略，以及同一实例中头文件新增、删除、恢复的实际同步。C 另外在同一测试中检查同步仍读取原目标节点，以及异常后恢复模式。

## 候选 B 的冷进程 sync

每个项目 13 个场景，每种版本各执行一次，共 52 次。每次启动新 Node 进程，按场景交替版本顺序，计时为完整 `await sync()`，包含引用处理及收尾。项目镜像只含索引内文件与适用的 ignore 规则，不含 `.git`，因此绝对时间不等同于原项目的日常 CLI 时间。

MAME 镜像为 23,380 文件、554,646,599 字节；OceanBase 为 14,347 文件、392,728,220 字节。复制时验证每个文件的内容哈希与种子一致，并保留同步比较所用的毫秒时间戳。两版使用同一个种子的独立数据库副本。MAME 镜像与完整 init 相差历史 Git/ignore 扫描范围中的 `3rdparty/genie/src/host/scripts.c`；只在相同范围内做版本对照。

单位：秒。空同步为 4 次均值；源文件改写、添加函数及头文件修改各为 2 次均值；新增、删除及恢复各一次。场景按顺序进行，第一次建立上下文与后续运行的状态不同，均值是场景集合平均，不是相同输入的重复测量。

| 场景 | MAME 基线 / B | OceanBase 基线 / B |
|---|---:|---:|
| 空同步 | 2.268 / 2.255 | 0.331 / 0.351 |
| 追加注释／移除测试函数 | 15.168 / 15.231 | 5.146 / 5.131 |
| 源文件语义修改 | 12.090 / 12.137 | 4.448 / 4.472 |
| 头文件注释修改 | 28.278 / 28.494 | 4.576 / 4.615 |
| 新增文件 | 5.929 / 5.907 | 3.086 / 3.076 |
| 删除文件 | 2.322 / 2.295 | 0.393 / 0.388 |
| 恢复文件 | 26.519 / 26.367 | 4.724 / 4.742 |

B 没有显示普通 sync 的明显加速。源码/头文件修改的均值变化约在 −0.3%～+0.8%；MAME 头文件两次分别为 31.345 / 32.055 秒和 25.212 / 24.932 秒，方向不一致。OceanBase 空同步平均多约 20 毫秒，保留这一观察，不用百分比掩盖绝对差值，也不将这些小样本直接当作稳定性能结论。

原始脚本中的 `comment-1` 是追加注释，`comment-2` 同时移除了上一阶段加入的测试函数。因此两者合并的数据不代表“纯注释同步”性能。连续同步另外覆盖了直接改名并更新调用。

## 连续同步的复核

每个版本、每个项目在同一实例中运行 7 次指定文件同步：首次空同步、三次函数/调用修改、恢复、两次空同步，共 28 次。全部场景检查通过，但最初这轮 B 中，MAME 首次语义修改为 13.834 / 15.840 秒，恢复为 6.547 / 7.187 秒；OceanBase 首次语义修改为 5.411 / 5.759 秒。不能忽略这些明显慢样本。

MAME 慢样本中，未改动的框架检测由 1.426 秒增至 1.700 秒，Worker 设置、解析、存储等也同时变慢；当轮没有记录独立的 CPU 采样，不能事后确定原因。因此追加反向/交错顺序的连续同步复测并记录负载，保留首轮原始结果。

MAME 按 B→基线、基线→B 两组顺序复测，首次语义修改分别为 14.474 / 15.638 秒、14.226 / 15.068 秒，均值 **14.350 → 15.353 秒，慢 7.0%**。第二、第三次修改和恢复的均值变化分别为 −5.1%、+2.8%、+3.7%。OceanBase 一组复测的首次修改变快，但第二、第三次修改变慢，不能概括为普遍退化，也不能只选有利场景。

上述连续实验分别从各版本的冷同步恢复库复制数据库。虽然完整图内容相同，物理数据库文件并不保证相同。因此又让两版从**同一份基线数据库文件**重新复制：MAME 的 B 首次修改为 13.213 → 13.628 秒（+3.1%），后续三次操作分别快约 2.2%、3.5%、3.8%。这缩小了首次慢样本的差距，但没有给出稳定的同步收益。

随后候选 C 在同步持久化的匹配阶段同时暂停两项优化，`finally` 恢复策略。两版仍从同一份基线数据库开始。MAME 做正反顺序两组，OceanBase 做一组；单位秒，MAME 是两轮相同场景均值，OceanBase 是单次。

| 场景 | MAME 基线 / C | 变化 | OceanBase 基线 / C | 变化 |
|---|---:|---:|---:|---:|
| 首次语义修改 | 14.047 / 13.977 | −0.5% | 5.410 / 5.238 | −3.2% |
| 第二次语义修改 | 6.457 / 6.292 | −2.6% | 1.407 / 1.395 | −0.9% |
| 第三次语义修改 | 5.984 / 6.339 | +5.9% | 1.390 / 1.386 | −0.3% |
| 恢复原文件 | 6.199 / 6.308 | +1.8% | 1.386 / 1.414 | +2.0% |

C 消除了此前 MAME 首次修改持续慢的现象。第三次修改两轮分别为 6.006 / 6.104 秒、5.963 / 6.574 秒，均值的 +5.9% 主要受到第二轮影响；不能据此断言 C 存在稳定 5.9% 的退化。选择撤回的理由是收益偏小、内存代价及同步验收尚不充分，而不是已经证明每种范围都会导致固定比例的同步退化。

另外从固定 MAME 数据库重放 30,856 条头文件相关失败引用，分 183 组；先热身，再正反顺序测两次。基线、仅快速返回、两项同时开启均值为 11.549、11.524、11.496 秒，差异不到 0.5%，结果指纹相同，均无新增成功解析。没有证据支持用 import 缓存解决这类重试成本。

## 完整图正确性

六组完整内容比较通过：两个项目各自 A 的完整 init、B 冷进程 sync 恢复后、B 首轮连续 sync 恢复后。节点及文件没有增删或业务字段变化，所有边的来源、目标、类型、位置、元数据和 provenance 一致，未解析引用多重集一致；各组均 `pending=0`、外键检查无违规。C 通过场景内正确性断言和上述 255 项回归测试，没有再做完整数据库对比。

比较排除节点更新时间和文件索引时间。边及引用如果连内部行 ID 都相同，就逐 ID 比较全部业务字段；否则回退到边身份和引用多重集比较。完整 init 和冷进程 sync 的四个优化版数据库均通过 SQLite `quick_check`；连续 sync 已做完整内容和外键检查，没有再重复 `quick_check`。

三种范围及复测共执行 258 次 sync；各场景均完成、文件错误为零、pending 为零，新增/改名调用和恢复断言通过。测试涉及的两个真实项目源文件及全部镜像目标/头文件均与保存的原文哈希一致。真实项目原有索引未用于写入。

## 后续优先级

本轮不继续叠加缓存，也不扩大名称或覆盖关系预取。更值得先独立验证的是 init 的引用 Worker 动态领取分块：现有固定分配可能等待慢 Worker，而普通小范围 sync 不经过该池，容易明确收益和影响范围。其次是高扇出头文件的增量写库及安全的失败重试判定，直接针对已有日志中删除、重连、重复匹配的耗时。两者都需单独测量；本报告不承诺尚未实测的提速比例。
