# 名称评分优化：MAME init 与 sync 验收

2026-09-10，Windows、Node v24.11.1、`--liftoff-only`。对照 `dde73cd` 与本地候选提交 `85b3045`。验收目标是确认 MAME 和增量同步没有因 OceanBase 的优化而出现可重复的性能退化，并检查图数据一致性。

性能结论：本轮没有复现需要撤回 `85b3045` 的明确速度回退，可继续保留为本地候选；MAME 基本持平，不宣称稳定提速。新版 MAME init 峰值 RSS 增加约 0.53 GiB，作为已观察到的代价记录。本轮未执行合并、打包或发布，也没有追加产品源码修改。

## 对照范围

- 两份独立构建只在 `resolution/index.js`、`resolution/name-matcher.js`、`resolution/text-cache.js` 不同；其他 JavaScript 文件逐一校验相同。没有加载此前 parse/store 或 worker query/CPU 剖析钩子。
- MAME 完整 init 使用真实根目录 `D:\c_proj\mame`，每次创建新的数据库，连续运行旧、新版本，保持默认自动 Rust 宏扫描和相同的轻量阶段计时钩子。
- 本轮旧版完整运行相对历史种子多保留 `3rdparty/genie/src/host/scripts.c` 一个生成文件（390,275 字节），其余已索引文件的内容指纹全部相同，MAME HEAD 仍为 `57cf29e2c75e24ac168d35a418cbd6d26113088e`。历史文件数量断言因此拦停了控制脚本；核对差异后单独续跑新版，按本轮相同输入范围验收。该文件被 Git 跟踪，同时匹配 `3rdparty/genie/.gitignore:4`；Git 文件清单与文件系统回退路径对这种文件的处理不同，符合观察到的范围差异。扫描器在两个对比构建中相同，本轮不修改扫描规则，也不与历史不同范围的总耗时混比。
- sync 使用相同初始数据库的独立副本和源码镜像。MAME 镜像包含 23,380 文件、554,646,599 字节；OceanBase 包含 14,347 文件、392,728,220 字节。每个文件均校验内容 SHA-256 与索引一致，并保留 sync 使用的毫秒时间戳；复制精度导致的 12 / 5 个时间戳在原毫秒桶内校正。
- 镜像只含索引内文件及适用的忽略规则，没有复制 `.git`。MAME 在镜像中使用文件系统遍历，并再次检查文件存在性和 stat；OceanBase 使用扫描结果中的元数据。这些绝对耗时属于镜像环境，用于同一输入下的版本比较，不能直接作为真实工作区的日常 sync 耗时。
- 所有修改只发生在镜像中，源码和既有项目索引不变。计时覆盖完整 `await sync()`，含引用解析、关系合成、维护及 WAL 收尾；数据库打开时间另记。没有用提取层的 `SyncResult.durationMs` 代替完整时间。
- CPU 采样中的 `externalCores` 是主 Node 进程以外的 CPU 估算，也会包含该次运行启动的 Rust 扫描子进程；不把它直接等同于纯后台负载。完整 init 另记录引用阶段的样本，避开前置宏扫描子进程。

## MAME 完整 init

两次均为 8 个提取 worker、6 个引用解析 worker，Git 可用，Rust 宏扫描成功。每版一次完整运行，SDK 初始化至索引完成的总耗时如下：

| 环节 | dde73cd | 85b3045 |
| --- | ---: | ---: |
| 扫描、提取、写入 | 392.514 秒 | 392.798 秒 |
| 二级索引及 FTS | 47.005 秒 | 46.956 秒 |
| 引用解析及索引恢复 | 364.838 秒 | 358.646 秒 |
| 关系合成 | 101.249 秒 | 102.146 秒 |
| 维护 | 4.831 秒 | 4.809 秒 |
| **完整 init** | **911.155 秒** | **906.038 秒** |
| 采样 RSS 峰值 | 10.824 GiB | 11.350 GiB |

总耗时约 15 分 11 秒 / 15 分 6 秒，新版短 0.6%；引用阶段短 1.7%。未修改的提取阶段几乎相同。本轮没有复现此前单次全量约 10% 的变慢，但这组小差异也不足以证明 MAME 有稳定提速。

引用阶段外部 CPU 采样均值为 0.885 / 0.856 核，最大值为 1.534 / 1.265 核，分别 69 个样本。新版峰值 RSS 高约 0.53 GiB（4.9%）；新增缓存有保留预算，单次 RSS 差值仍受 GC 和分配器影响，不能全部归因于缓存。这项内存代价保留在验收结果中，不用 OceanBase 的内存下降掩盖它。

两次均完成 23,381 文件、1,614,526 节点、8,613,227 边，最终未解析引用 1,054,432；`complete=true`、文件失败 0、`pending=0`。

## 同一进程连续 sync

每版每项目在一个 CodeGraph 实例中执行 7 次同步，覆盖空同步、三次指定路径的语义修改、恢复、最终空同步，共 28 次执行。测试覆盖核心实例缓存生命周期，没有计入 watcher 的事件合并和 debounce 延迟。

| 场景 | MAME 旧 / 新 | OceanBase 旧 / 新 |
| --- | ---: | ---: |
| 首次局部语义修改 | 15.12 / 15.17 秒 | 5.52 / 5.12 秒 |
| 第二次局部语义修改 | 6.44 / 6.51 秒 | 1.42 / 1.39 秒 |
| 第三次局部语义修改 | 6.57 / 6.40 秒 | 1.44 / 1.33 秒 |

首次修改会建立全项目宏上下文，后续修改复用它，因此分开报告。MAME 最终空同步后的 RSS 为旧版约 1,674 MiB、新版约 1,667 MiB；OceanBase 约 446 / 436 MiB。这是有限序列的采样值，不是长时间运行的内存上限证明。

## 其他优化空间

### 首次 sync 的兼容修复

`QueryBuilder.repairLegacyCppIncludes()` 一次性修复旧 C/C++ include 目标和失败引用尾键，目前会将全部失败 C/C++ include 重新置为 pending，包括当前引擎新建库中已使用正确文件名尾键的引用。因此新库首次空同步仍出现明显额外工作，本轮 MAME 约 12.9 秒，OceanBase 约 9.9 秒；之后稳态空同步显著缩短。

可优先验证仅重试尾键确实不符合当前规则的旧行，并继续修复错误的成功 include 边。需要覆盖旧库升级、正确尾键保持不动、失败回滚、随后添加缺失头文件的恢复；不应直接跳过所有旧库修复。

### 高扇出头文件的存储和失败重试

MAME 首次修改 `device.h` 的旧版日志：存储约 5.3 秒，其中旧图快照约 1.6 秒、删除约 2.9 秒、重连约 0.7 秒；WAL 约 179 MiB。随后重试 6,168 个来源文件的 30,856 条失败引用，匹配约 13.0 秒，最终新增解析结果为 0。

可以研究对提取业务数据没有变化的节点/边做增量更新，减少删除和级联重连；也可完善安全的变更证明，减少无效失败重试。必须保留注释/预处理器/宏、源位置变化、重载签名、删除后引用复活的语义，不能通过跳过大候选集合或限制重试数量提速。

### 冷进程宏上下文和路径探测

单个 C++ 文件的冷 sync 仍需扫描全项目宏上下文，MAME 本轮约 2.7 秒。可评估按文件内容和引擎版本持久化宏贡献，增量合并冲突定义；新增、删除及宏修改时必须使缓存失效。连续进程已复用上下文，不能把冷启动收益外推到每次 watcher 同步。

此前 OceanBase 采样也显示 `canonicalFilePath` 的路径探测成本。可以减少明显无效的文件候选和重复探测，但须保留符号链接、大小写、外部路径及失败回退规则。它与名称评分属于不同优化点，应单独实验。

### 完整索引的引用调度

`ResolverPool.resolveBatch()` 将 5,000 条引用分为 10 个 500 条分块，预先分配给 6 个 worker，分块代价不同时会等待较慢的 worker。可实验更灵活的任务分配，并保持返回顺序。另一方向是借鉴社区的计算与清理重叠，但下一批必须看见已提交的边，还要验证尚未删除的 pending 继承引用是否影响查询。普通小范围 sync 不使用该 worker pool；实验仍需覆盖 sync 的大规模中断恢复路径。
