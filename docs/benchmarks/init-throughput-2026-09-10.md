# init CPU 利用率与吞吐分析

生产基线为 `c5cf847`；`f3dcf9d` 仅增加上一轮未采用候选的报告。本轮修复提取窗口供给不足，完整 init 实测 MAME 缩短 15.8%，OceanBase 缩短 16.8%。八组完整图内容比对、116 次 sync 场景检查及 157 项回归测试通过；交错复测没有复现稳定的 sync 退化。建议保留本轮改动，工作保存在本地分支 `perf/init-throughput`。

## 观测方式

独立诊断脚本 `scripts/profile-init.cjs` 通过 Node 的 `--require` 显式加载，同时设置 `CODEGRAPH_PROFILE_OUTPUT` 和 `CODEGRAPH_PROFILE_BUILD`。正常 init/sync 不加载它，没有新增默认统计逻辑。

脚本记录当前线程 CPU、Worker 任务发出/开始/结束/收到回复的时间、解析和写入队列、主线程批量数据库操作、GC 以及进程 CPU/RSS。主线程和 Worker 之间的诊断字段在进入业务处理前移除，保持原消息内容。支持版本没有 `process.threadCpuUsage()` 时，线程 CPU 为 null，不以整个进程 CPU 冒充单个 Worker 的 CPU。

时间范围有明确区分：

- 任务发出至 Worker 开始包含消息传输、反序列化、事件调度和队列等待，不能全部称为纯排队时间。
- Worker 结束至主线程接收包含返回消息传输和主线程延迟。
- 异步方法和嵌套方法的时间范围会重叠，不能把所有计时直接相加。
- Worker 实际运行的累计时间除以阶段墙钟时间，用于估算平均并行度；同样不能把累计 CPU 秒当成 init 墙钟秒。
- 全机磁盘计数器反映物理磁盘整体负载，不能直接归因于单个进程。Rust 辅助进程也不在 Node 进程 CPU 内。

## 实验设计

测试环境为 Windows、Node v24.11.1、32 个逻辑处理器。完整剖析顺序为 OceanBase、MAME，各运行一次默认 8 个解析 Worker、6 个引用 Worker，使用当前生产代码的冻结构建。实际源目录为 `D:/c_proj/oceanbase`、`D:/c_proj/mame`，数据库单独写入当前工作树。全部完整剖析和并发实验顺序运行，不互相争用 CPU；计时期间不运行测试或数据库全量比较。

引用并发实验在各仓库固定的提取后数据库上只读运行，取四个位置各 50,000 条引用。每个配置新建 Worker 池，先热身 20,000 条，再测量相同的 200,000 条；每批 5,000 条、每个分块 500 条不变。分别比较静态调度的 2/4/6/8/12 Worker，以及动态调度的 6/8 Worker，正反顺序各一轮。

动态实验仅在一批内部由空闲 Worker 领取下一个分块，结果仍按分块顺序合并；没有让下一批提前读取未提交的图。这一只读重放可以比较调度和并发趋势，但不执行真实 init 的跨批次写入，不能替代完整 init 验收。

原始数据和运行脚本保存在 `bench-logs/init-throughput-20260910/`。所有实验目录拒绝覆盖既有输出；两个真实项目的源码和原有索引不用于写入。

OceanBase 的第一轮完整观测为 695.435 秒，文件、节点、边及失败引用数量与生产基线一致，`complete=true`、文件错误为零、pending 为零。该时间包含诊断开销，用于定位瓶颈，不作为候选提速的验收数据。

| OceanBase 阶段 | 墙钟耗时 | 平均进程 CPU | 平均主线程 CPU |
|---|---:|---:|---:|
| 提取及写入 | 269.078 秒 | 3.82 核 | 0.08 核 |
| 引用处理主循环 | 275.203 秒 | 3.44 核 | 0.30 核 |
| 引用索引恢复 | 22.523 秒 | 1.02 核 | 0.99 核 |
| 关系合成 | 90.061 秒 | 1.02 核 | 0.97 核 |

提取阶段的 14,347 次解析累计执行 760.463 秒、当前 Worker 线程 CPU 累计 743.361 秒；对应写入累计 41.591 秒、线程 CPU 41.188 秒。写入回压等待累计仅 0.751 秒。采样中解析池平均有 5.02 个空闲 Worker，63.4% 的采样时间只有至多两个 in-flight 解析任务且队列为空。最长文件 `src/share/ob_rpc_struct.cpp` 的解析墙钟 51.274 秒、线程 CPU 50.547 秒。实际任务大部分时间在计算，空闲更值得从任务供给和有序窗口调查。

引用阶段在 Worker 池内等待 206.245 秒，其他主线程步骤约 68.958 秒。后者主要为读取引用 10.628 秒、构造边 14.997 秒、插入边 27.736 秒、删除已处理引用 10.539 秒、更新失败引用 4.114 秒。池内所有任务累计执行 820.327 秒，相当于池工作区间平均约 3.98 个 Worker 在执行，而配置为 6 个；分块不均和两轮分配值得继续验证。

磁盘计数器中，提取与引用主循环的全机磁盘队列长度 P95 均为零，采样均值分别为 0.038 和 0.029；结合解析、写入和引用任务的 CPU/墙钟接近程度，没有证据表明持续磁盘拥堵主导了这次运行。少量读延迟尖峰仍保留在原始数据中，不据此推断所有机器都不受 I/O 限制。

这些观测将本轮优化重点指向有序提取窗口：保持执行中的读取/解析任务上限及原字节预算，允许更多已经完成的结果等待原顺序写入，并在前序文件未完成时补充空闲执行槽。低 CPU 利用率是线索；这里结合队列状态和任务 CPU 时间，才定位到可修复的供给不足。

## 提取窗口候选

原来的 `maxPending` 同时限制正在执行和已完成但尚未写入的文件。头部文件慢时，后续结果完成也不会释放数量窗口；空闲解析 Worker 得不到新的任务。

候选新增可选的总缓冲数量上限，将未完成任务和完成结果分开计数。默认参数仍保留原窗口语义；全量索引的多 Worker 路径使用每 Worker 128 个总缓冲位置。本次 8 Worker 对应最多 1,024 个未消费条目，未完成的读取/解析仍最多 32 个。原字节预算不变，完成结果和等待写入的当前结果始终保留字节记账；一个文件的结果超出估算仍按原规则暂停新任务。实际 RSS 不是字节预算的硬上限。

任何任务完成都可以唤醒补充任务的循环；输出仍严格按输入顺序。头部已完成时最多补充一个任务便交还给写入端，避免为了填满较大的缓冲窗口而拖延写入。后续失败立即被观察，但按原顺序传播；取消和写入失败会关闭源迭代器，晚到结果不再写入。

回归测试覆盖窗口补充、未完成任务和总缓冲上限、源文件及完成结果的字节预算、超大文件、及时交付、取消、按序失败，以及观测脚本消息透明性和 transferable typed-array。

OceanBase 配对结果（先候选、后基线）：提取阶段 **265.470 → 157.680 秒，缩短 40.6%**；提取后索引恢复 32.913 → 33.285 秒；采样峰值 RSS 2.653 → 3.042 GiB。两版均为 14,347 文件、926,980 节点、920,365 条提取边、5,708,513 条待解析引用。此结果仅覆盖提取及其索引恢复，不是完整 init。

MAME 配对结果（先基线、后候选）：提取阶段 **380.176 → 174.827 秒，缩短 54.0%**；采样峰值 RSS 4.299 → 4.625 GiB。两版均为 23,381 文件、1,614,526 节点、1,650,803 条提取边、7,851,814 条待解析引用。

同一组提取观测中，MAME 平均进程 CPU 从 4.26 核提高到 7.11 核，OceanBase 从 3.85 核提高到 6.02 核；解析池平均空闲 Worker 分别从 4.46 降至 2.13、4.95 降至 3.15。等待有序输出且仍有空闲解析 Worker 的采样占比分别从 73.8% 降至 30.7%、79.9% 降至 44.2%。本轮减少了供给不足，但长文件尾部及字节预算仍限制并行度，不能据此承诺用满 32 个逻辑处理器。

两个提取后数据库均已完成全部内容比较。节点和文件排除索引生成时间，其余业务字段、边字段及待解析引用全部按相同行 ID 逐项一致；外键检查为空、SQLite `quick_check=ok`。这比仅比较总数更强。提取后仍有 pending 是预期状态，完整 init 才要求其归零。

运行时构建逐文件校验仅 `extraction/index.js` 和 `extraction/ordered-pipeline.js` 改变；引用解析、同步处理和原生辅助程序保持一致。普通增量 sync 不经过本次调整的 `indexAll()` 有序窗口；触发全量重建时才使用它。仍对真实 sync 场景测量，不以代码路径未变代替性能验收。

## sync 与最终验收

两个仓库各 13 个冷进程场景、每版各一次，共 52 次；各版同一实例另运行 7 次连续同步，共 28 次。覆盖空同步、源码修改、调用改名、头文件修改、新增、删除和恢复。冷进程计时为完整 `await sync()`，不包含 CLI 加载和数据库打开；“冷进程”不等同于清空操作系统文件缓存。

源文件修改发生在隔离镜像中，真实项目源码不写入。初始数据库来自相同基线种子的独立副本，镜像沿用上一轮的 Git/忽略范围：MAME 为 23,380 文件，完整 init 为 23,381 文件，差异是 `3rdparty/genie/src/host/scripts.c`；每组前后对照范围一致。全部场景均完成、文件错误为零、pending 为零，场景断言通过。完整系列结束后确认镜像的目标源码及头文件恢复到原始内容。

### 慢样本复核

首次 MAME 注释修改为 19.462 → 22.334 秒，多 2.872 秒，其中宏扫描多 1.902 秒、文件扫描协调多 0.717 秒；修改引用匹配只多 0.021 秒、失败引用重试匹配多 0.137 秒。这支持优先控制扫描缓存和运行顺序，但不足以直接宣布候选无退化。

因此补充两个控制：两仓库各用相同新种子、每次一致地预热源码读取，按候选/基线/基线/候选交错运行首次注释修改；MAME 热态另用完全相同的原始数据库种子，按同样顺序运行四组连续同步。后者针对前一组约 9% 的慢样本，排除使用各版前序 sync 输出数据库带来的影响。这两项控制共增加 8 次和 28 次 sync，总计 116 次；全部场景检查通过，源文件在最后恢复。

本轮不采用增加引用 Worker 或动态分块调度：只读实验未证明两项目同时获益，且增加内存和累计 CPU 工作。更值得单独验证的是引用阶段的批量数据库读写及关系合成中的串行工作；跨批次重叠必须保持提交顺序和引用可见性，不能直接让多批并发读写。Rust 能否有帮助取决于被搬迁的计算热点；仅改写当前空闲等待逻辑，并不会自动得到多核收益。
