# Windows 文件系统身份边界修复

基线：`f156dbce`。仅针对服务身份与源码授权的 Unicode 大小写碰撞。

## 问题与方案

JavaScript `toLowerCase()` 会将 `K` 和 `K` 合并，但这不代表 Windows 将两者视为同一个目录。不能用语言层 Unicode 折叠代替文件系统身份。

- Windows 管道身份使用现有目录的 `stat({bigint:true})` 设备/卷与 inode/文件 ID，严格会话和服务握手使用同一物理身份比较。
- Windows 源码授权在真实目标路径的祖先中查找与授权根相同的物理目录身份，不以小写字符串前缀授权。
- 无法取得非零文件 ID 时，安全比较拒绝；管道命名仅退回不折叠的原始绝对路径，不将不同名称合并。
- POSIX 服务身份保持原有路径语义。词法边界只折叠 ASCII，最终授权仍通过真实文件身份；realpath 缓存不再合并不同拼写。

服务只管理已初始化项目，正常情况下图谱目录已经存在。重新创建数据目录会改变文件 ID，因此须停止旧服务后重建/重启；升级前需使用原版本停止旧 daemon，不自动接管旧管道。

## 验证

先在基线运行三个新增用例，全部失败：K/K 身份碰撞、目录别名不能共享 IPC 身份、授权 K 后可经嵌套链接读取 K 文件。修复后通过。

Linux 上使用真实不同目录及目录软链接，切换 Windows 平台分支验证物理身份逻辑。这不是 Windows 实机验收。另加入 Windows 原生 ASCII 大小写管道一致性用例，在当前 Linux 环境跳过。

完整 Windows 命名管道、NTFS 文件 ID 和 junction 端到端结果仍需 Windows CI/实机验证。不承诺消除 realpath/stat 与后续读取间的并发文件系统竞态。

本方案依赖文件系统提供稳定的非零卷/文件身份。网络文件系统或非 NTFS 上的行为未验证，不宣称这些环境已支持。

最终验证：构建通过；7 个定向套件 93 项通过、4 项跳过。跳过包括 Windows 原生验证和既有平台限制项。额外覆盖零文件 ID、stat 失败及不存在路径拒绝。
