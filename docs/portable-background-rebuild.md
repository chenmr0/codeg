# 单库便携与后台重建

本实现基于 `1.1.3-sync-quick` 重新整理固定路径发布流程。目标是让
`codegraph.db` 成为唯一需要分发的索引资产，同时在后台重建期间继续查询旧库。
只有新库准备完成后的发布阶段才短暂关闭读者准入。

本文描述当前实现和使用边界，不代表全部平台已经验收。

## 1. 文件布局与运行环境

支持原生 `node:sqlite` 的运行环境中，新建项目使用固定活动文件：

```text
.codegraph-wx/
  codegraph.db
  codegraph.db-wal / codegraph.db-shm    # SQLite 运行期间可能存在
  .runtime/portable/
    gate.sqlite                        # 当前发布状态与修订号
    writer.sqlite                      # 写入及发布者互斥
    readers.sqlite                     # 连接共享租约及发布排他屏障
    <operation-uuid>/
      candidate.db                     # 尚未发布的新库
      old.db                           # 切换中的旧库备份
```

协调 SQLite 自身也可能产生 WAL、SHM 或 journal。日志、daemon 通信文件及
既有辅助文件不因本功能自动移入或合并到主库。`CODEGRAPH_DIR` 仍决定项目内的
数据目录；既有 `.codegraph` 的目录发现规则继续保留。

`gate.sqlite` 只保存一条当前状态记录及当前发布事务，不新增永久操作历史表。
首次初始化在同一事务提交 schema、单例状态和就绪版本；未完成的首次建库可以重试，
已经标记就绪却缺少结构的协调库则拒绝静默修复。
`writer.sqlite` 和 `readers.sqlite` 使用 SQLite 事务承载操作系统文件锁，
不能用 PID 是否存在或文件年龄代替锁的所有权判断。

原生后端不可用时，新建项目继续使用原有平面数据库路径，不能据此宣称后台
固定路径发布已经可用。不要让缺少该协议的旧版本进程、外部 SQLite 工具或不同
运行环境共同写入同一数据库。

## 2. 哪些信息随数据库移动

图谱、文件记录、内容 hash、版本和配置等索引信息仍保存在主库。新增或沿用的
`project_metadata` 记录包括：

| 键 | 含义 |
| --- | --- |
| `portable:database-id-v1` | 数据库实例标识 |
| `portable:source-catchup-v1` | 发布后尚未完成的源码核对义务 |
| `adaptive:cost-history-v1` | 有界的耗时样本，最多保留最近 96 条 |
| `adaptive:index-config-v1` | 已索引配置指纹 |
| `adaptive:source-owner-v1` | 自动重建所需的源码归属信息 |

成本样本是可忽略的性能提示，不决定数据库是否有效。规划只使用匹配当前运行
指纹的样本；指纹包含工作区、实现、提取器、平台、Node 和运行参数等信息。
复制来的其他环境样本不会因留在库中就被无条件套用。原目录的成本 JSON 不作为
portable 模式的成本来源。

数据库实例标识不代表用户已完成安全导入。恢复逻辑仍需检查文件、SQLite
完整性、sidecar 和操作系统锁，不能仅凭 ID 不同就删除旧状态。

## 3. 后台构建与短暂停顿发布

1. 在独立发布进程中取得写入互斥，重新规划并记录候选构建意图。
2. 在同一文件系统的私有操作目录构建 `candidate.db`。这一阶段旧库仍接受
   查询；其他图谱写入等待。旧库反映上一次完成的索引，不承诺已经包含最新源码。
3. 完成候选索引、完整性和源码校验，将待补查标记写进候选数据库，再封存候选。
   完整库 hash 等重工作安排在暂停准入之前。
4. 将状态设为 `draining`，停止新读者进入，等待在途请求及实际 SQLite
   连接释放。连接关闭后还须等待后台维护 worker 真实退出，才能释放读租约。
5. 完成最终 checkpoint，确认不存在影响替换的 sidecar，记录 `replacing`，
   将旧库改名为备份，将候选改名为固定的 `codegraph.db`。
6. 标记提交、增加修订号并恢复准入。后续查询重建连接与缓存；正常情况下回收
   本次候选目录和旧库备份。
7. 根据新库里的待补查标记进行全内容核对。发现发布附近发生的源码变化时继续
   修复；只有内容、配置及持久恢复工作都满足要求后才清除标记。

默认发布排空预算为 1 秒。这个值不是总暂停时间或端到端同步耗时的硬保证：
文件系统 rename、fsync、重开及失败恢复仍取决于运行平台。排空或切换前检查
超时会保留旧库；已经进入 rename 的异常需要先完成恢复判断。

同步查询在发布窗口内可能收到 `PORTABLE_BUSY`；部分异步读入口会有界等待重试。
因此“旧库可查”指后台构建阶段保持服务，不代表发布窗口内所有调用都无等待、
无重试。MCP 请求需要使用同一个读 pin 覆盖请求中的相关读取。

## 4. 大变更策略与补查

重建选择发生在执行前，不是增量任务运行超时后直接中途切换。规划结合可用的
耗时样本、配置及版本变化和结构性变更条件；样本不足时使用现有保守阈值。
单独达到 128 个变更文件并不意味着一定重建，具体条件见 `adaptive-plan.ts`。

后台重建失败后，父进程先等待子进程退出并完成受控恢复，再决定是否退回增量。
取消、恢复失败和必须重建的配置变化不会被简单吞掉。若新库已经发布，库内补查
义务仍优先执行，不能因 `adaptive:false`、限定 `paths` 或重新打开而丢失。

全量补查检测到同大小、同 mtime 的内容变化时，通过 `forceReindexPaths`
绕过普通增量的 stat/hash 快路。普通同步保留的 stat 性能取舍，不等同于全量补查。

## 5. 只替换一个公共数据库

支持的流程是**离线替换**：

1. 发布端正常停止写入，完成 checkpoint，提供不依赖 WAL 的完整单文件快照，
   或使用合适的 SQLite backup 流程生成一致快照。
2. 接收端停止全部相关 CLI、MCP、daemon、SDK 和外部 SQLite 程序。没有前台
   请求不等于离线；后台 worker 也必须退出。
3. 对 SDK，先结束或取消并等待在途操作，再调用 `close()`，并等待
   `whenIdle()` 完成维护线程退出。不要在仍有请求时强行关闭。
4. 仅替换数据目录中的 `codegraph.db`，保留接收端本地 `.runtime`。
5. 重启并读取新库。源码版本、配置和 schema 仍须与使用场景兼容；返回源码的
   能力仍依赖相应工作区文件。

当前 portable 打开入口要求数据库已具有当前 schema，尚未提供旧 schema 根库的
受协调自动升级入口。旧版社区数据库不是无条件即插即用；请先在隔离目录用兼容
版本迁移或重新生成当前版本索引，再按上述离线流程导入，保留原库备份。

不要混用旧库的 `-wal`、`-shm`、`-journal` 与新主文件，也不要为了让替换成功而
直接删除可能含有恢复数据的 sidecar。应先通过正常关闭、checkpoint 或明确恢复
处理这些文件。

新目录只有完整根库、没有 `.runtime` 且没有 `CURRENT` 时，在原生后端可用的
条件下会建立本机 portable 协调，不要求携带发布端的运行目录。运行目录包含
本机锁和绝对路径，不是分发资产。

## 6. 崩溃恢复与外部导入

恢复按当前事务阶段检查：

- `building`、`prepared`：保留有效活动库，撤销未发布意图；可安全清理的候选
  会被回收。带未知文件或 SQLite 恢复文件的目录保留证据。
- `replacing`：取得写入互斥和读者排他屏障，检查旧库、候选和备份的 SHA256
  拓扑，选择保留旧库、恢复旧库或确认已经完整安装的新库。
- 如果 `replacing` 时发现活动库是另一份完整、独立导入的数据库，且没有
  阻塞的连接和 sidecar，验证后接管活动库，保留原候选与备份证据，不让旧恢复
  记录把它覆盖回去。
- `committed`：验证当前活动库，清除当前事务并尽力清理；不会因活动库后来
  被正常离线替换而把历史备份重新发布。

损坏文件、身份无法解释的组合、缺失锁文件、未知 sidecar 或活跃占用不会通过
强制删除来绕过。异常证据目录可能被保留，不承诺所有失败都能自动清空目录。
正常重建不会无限积累终态事务记录，但证据保留仍可能占用磁盘，需要诊断处理。

这套协议只保护使用相同协调入口的进程。**运行中的外部 cp/覆盖不受支持**；
把所有业务元数据放进主库也不能让活跃 SQLite 连接自动安全地跨文件替换。

## 7. 旧 CURRENT 布局兼容

新建 portable 索引不产生 `CURRENT` 或 `generations`。已经使用 `CURRENT`
且尚未建立 portable 协调的目录，继续沿用基线的旧代际路径；本次没有新增自动
迁移或自动删除历史代际目录的命令。不要把“保留兼容”理解成旧目录已经迁移。

已经建立 portable 协调的目录以根 `codegraph.db` 为活动文件，不能依赖残留
`CURRENT` 重新指向旧库。需要处理混合布局时，应先停止进程、核实文件归属和
恢复状态；不要通过复制整套其他机器的 `.runtime` 进行迁移。

## 8. 验证与尚未覆盖的保证

构建后可运行新的生产入口与协议验收：

```sh
npm run build
node --test scripts/tests/portable-protocol-bootstrap.test.cjs scripts/tests/portable-rebuild-acceptance.test.cjs
```

测试覆盖小型真实源码夹具、独立读者进程、固定根库、离线覆盖、同 stat 补查、
切换超时及阶段退出恢复等场景。测试源码存在不等于本机本次全部通过；请以实际
运行结果为准。

Windows 尚未在本轮开发环境实测。需在真实 Windows 上验证全部句柄和 worker
退出、rename 行为、长请求排空及恢复路径；Linux 通过不能替代 Windows 验收。
实现没有声明 Windows 目录 fsync 的断电持久性。进程退出注入测试也不等于断电
测试。大仓查询延迟、真实切换暂停和完整重建总耗时仍需独立测量。
