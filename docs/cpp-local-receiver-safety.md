# C++ 局部对象错连：有界修复与性能验证

日期：2026-09-07。对照基线：`4849bc1`。本轮不修改 Rust、WASM、数据库 schema 或失败引用的选择规则。

## 修复范围

原问题：`PictureData data; data.flatten()` 曾正确连接到 `PictureData::flatten`；删除定义文件后，名称回退却选中了另一个类的 `flatten`，恢复文件后仍保持错误连接。

本轮仅在原来的 C++ 类型方法匹配失败后，检查简单显式局部声明。如果声明与调用处于同一函数的有效块作用域、类型拼写和访问方式可核验，且没有已知间接类型/继承关系，则保持未解析，等待真正的方法恢复，不再猜测别的类。正常类型匹配成功时不运行这个检查。

新增约 131 行生产代码、删除 4 行，涉及 4 个生产文件。其中 92 行是独立的文本证据检查，继承声明状态复用现有缓存。

保留原路径的情况包括：

- 宏、类型别名、模板类型；值/引用对象的 `operator->` 代理行为。
- 已声明继承，包括还未解析成功的基类；未提供继承证据接口的外部解析上下文。
- `auto`、复杂绑定、遮蔽、已结束的块作用域、条件编译、lambda 等无法核验的形状。
- 超过检查预算、无法读取源码、引用位置不匹配或没有可靠函数节点。

这不是完整 C++ 类型推断，也不修正原类型推断“已经返回成功但实际猜错”的所有情况。枚举别名、复杂接收者和声明/定义逻辑身份仍另行处理。

## 正常功能保护

初版确实引入过一个反例：五层继承的方法超过现有类型查找深度后，局部声明检查挡住了原来可用的回退。已在交付前撤掉对继承类型的收紧，并补测“声明了基类但基类未解析”的情况。后者不能用空的已解析基类列表当作没有继承的证明。

`hasCppInheritance` 的正常路径复用类型查找已经读取的继承边和待解析/失败继承引用，只在现有缓存中附带一个声明状态；不新增逐引用 SQL 查询。缓存关闭的诊断模式另行读取相同事实，测试保证答案一致。

最终新增 36 个测试；相关专项总计 **1,208 通过、0 失败、4 个原有条件跳过**。覆盖构造/拷贝/指针/引用初始化、重复成员使用、中文/CRLF、注释/字符串/raw string、作用域、代理、宏/别名/模板、深层继承、未解析基类、缓存复用/淘汰、删除/重启/恢复。构建通过。

## 工作量与缓存限制

- 最多检查函数起点到调用点的 256 行、16K UTF-16 单元；先检查大小，再遮蔽文本。
- 接收者/类型名各最多 256 字符；超限直接保留旧路径。
- 同一个不可变行数组最多缓存 128 个调用点结果；弱引用键不阻止旧文本回收。
- 只缓存源码证据，不缓存方法存在性、匹配目标或继承图；同路径的新内容不会复用旧证据。
- 不新增全仓扫描，不扩大历史重试范围，不跳过原本应该进行的失败引用重试。

## 最终版本的性能对照

Windows、Node 24.11.1，同机交替顺序测量三轮，取各场景中位数；不是 Linux 大仓的耗时承诺。

### 实际 sync 的隔离压力场景

使用相同的 200 个 Skia 文件副本，加 20 个调用文件（共 2,000 个局部对象调用）及类型文件；初始 222 文件，约 2 万条已有失败引用。每个版本每轮从新的独立索引开始，测量前后重新打开数据库。

以下是验证脚本墙钟，包含开关库、`sync` 和相同的质量检查，不包含 Node 进程启动。两者均走目录 walk；基线归档不含原生扫描预编译件，候选探测后回退的约 2ms 也包含在表内，因此不把几个毫秒的差异解释成确定的优化收益。

| 场景 | 基线 | 最终候选 | 说明 |
|---|---:|---:|---|
| 稳定空同步 | 0.136 秒 | 0.133 秒 | 没有新增全库工作 |
| 20 文件追加注释 | 0.743 秒 | 0.760 秒 | 小幅波动 |
| 20 文件修改代码 | 0.722 秒 | 0.710 秒 | 小幅波动 |
| 普通新增 20 文件 | 0.534 秒 | 0.545 秒 | 约多 11ms |
| 删除 2,000 个调用的提供方 | 0.348 秒 | 0.348 秒 | 候选不再错误改绑 |
| 缺失期间新增 20 个同名方法文件 | 0.575 秒 | 0.641 秒 | 多约 66ms / 11.6% |
| 恢复提供方 | 0.467 秒 | 0.572 秒 | 多约 105ms / 22.5% |

首次 sync 的旧 include 内容修复另计：3.681 → 3.775 秒。这是基线已经存在的一次性内容修复，不能混入“稳定空同步”数字。

压力阶段不是零性能代价：候选真实保留了 2,000 条失败引用，并在恢复时处理它们；基线把这 2,000 条调用错误地标为成功，因此后续少做了恢复工作。候选最终 **2,000/2,000 正确恢复**，基线仍全部错连到 `SkPictureData::flatten`。所有步骤完成、错误列表为空、pending 为 0、悬空边为 0。

## 结论与使用边界

本轮风险可控，未观察到普通场景明显变慢；集中产生大量同名失败引用时仍会有实际重试成本。不能用这组测试外推所有大型 Linux 仓库，部署后仍应关注 `changedRefsMs` 和 `failedRefRetryMs`，尤其是大批删除/恢复。

已有数据库格式和提取版本不变，可以继续使用。本轮不会为了修复旧错误成功边在空 sync 中扫描全库；历史错误需要受影响调用方重新索引或 `index -f` 才能全面重算。

所有写测试均在自建临时项目完成并清理；OceanBase 原库 SHA-256 保持 `edd1bbd079572db23fe49eebab26b62ed7c556d50aa122e5d46f868423ae97d9`。原始测量、脚本及回归结果保留在本机 `release/cpp-local-safety-20260907/`。验收过程未发布 npm 包、未修改用户原项目；代码提交不等于完成大型 Linux 仓库的部署验收。
